# 主题生成器（Swift）

- 状态：draft
- 关系：扩展 AST-082 FR10、FR18 与 AST-093 FR4，并适用 AST-082 FR16 与 AST-006。它是主题到达 Swift 的唯一路径。

## 摘要

用 Astryx 构建的 iOS 应用展示自己的品牌，而不只是核心的默认品牌：任何 Astryx 主题——无论来自 neutral 这样的已发布主题包，还是来自产品自身——都会变成一个 Swift `Theme`，由 `.astryxTheme(.neutral)` 应用，并带有与 Web 相同的浅色和深色取值与字体。每个共享 token 都是带类型的 Swift 成员，因此拼错的 token 会编译失败，而不是什么都画不出来。生成器运行核心自己的解析器，因此 Swift 从不重新实现主题逻辑。

## 需求

- **G1 — 输入是可移植主题；由核心解析。** 生成器是一个函数 `renderSwiftTheme(theme, options)`。它的输入是一个 `PortableTheme`（name、tokens、主题本地 token；AST-082 FR18）。来自 `defineTheme` 的 `DefinedTheme` 可以原样传入，因为它是 `PortableTheme` 加上一个生成器会忽略的 Web 部分。在核心发布 `PortableTheme` 之前，输入类型是 `DefinedTheme`。取值仅来自核心的 `resolveThemeTokens(theme, {mode})`，分别以 `mode: 'light'` 调用一次、以 `mode: 'dark'` 调用一次。主题的 `[light, dark]` 元组到达生成器时已经拆分，每个模式一侧。取值任意深度处的 `light-dark(<light>, <dark>)`（整个取值，或位于 `color-mix()`、相对颜色或阴影层内部）在浅色模式下取第一个参数，在深色模式下取第二个。生成器从不直接读取 `theme.tokens`，也从不自行解析引用；它把每个已解析的 CSS 值转换成 Swift 值（G7）。
- **G2 — 核心只在构建时读取。** 生成器在构建时运行；生成的 Swift 只导入 SwiftUI，运行时不携带核心的任何内容（AST-082 FR16）。在核心的可移植入口发布之前，生成器在构建时通过 `@astryxdesign/core/theme` 和 `@astryxdesign/core/theme/tokens` 读取核心，这是 AST-082 FR16 允许原生构建脚本进行的构建时读取，二者都列入边界检查；一旦可移植入口发布，它只通过该入口读取核心。
- **G3 — 一个共享 token 类型，每个主题一个文件。**
  - `apple/Sources/Astryx/Theme/Generated/Tokens.swift` 声明带类型的 token 表面：`Tokens` 每组一个成员（`color`、`space`、`radius`、`size`、`font`、`shadow`），每组是一个 struct，每个 token 一个带类型成员，`font` 例外，其成员是 G6 命名的子组：每个类型样式一个 `TypeStyleTokens`，以及用于各刻度的 `FontFamilyTokens`、`FontSizeTokens` 和 `FontWeightTokens`。它由核心已解析的 token 名生成，这些名字对每个主题都相同（G5），因此它不依赖任何单个主题。
  - 类型名遵循 Swift 组件 API 规格：无前缀，位于 `Astryx` 模块中，因此 `Astryx.Theme.neutral` 和 `Theme.neutral` 命名同一个值。
  - 每个主题变成 `apple/Sources/Astryx/Theme/Generated/<SwiftName>Theme.swift`，它声明 `Theme.<swiftName>`，并带一个用于浅色的 `Tokens` 值和一个用于深色的 `Tokens` 值。
  - `<swiftName>` 是主题的 `name` 去掉开头的 `astryx-` 后的小驼峰形式（`neutral` → `neutral`，`y2k` → `y2k`，产品的 `acme-brand` → `acmeBrand`）。核心的默认值——核心在没有主题时解析的结果（`resolveThemeTokens(null, {mode})`）——是 `default`。不是合法 Swift 标识符、是 `default` 以外的 Swift 关键字、或与另一个生成主题重名的名字，会使运行失败。
  - 每个文件以头部开始，头部写明源包与主题名，注明“Do not edit”，并写明重新生成命令。头部从不写版本号，因此只提升版本的发布不会改变任何生成文件。
- **G4 — 输出是确定性的。** 相同的主题与相同的核心产出逐字节相同的文件：成员有序，数字采用其最短的精确形式，不含日期、路径或机器细节。
- **G5 — token 集合是一份契约。** 生成器保留核心已解析 token 名中的这些组：`color-*`、`spacing-*`、`radius-*`、`size-element-*`、`border-width`、`font-size-*`、`font-weight-*`、`font-family-*`，以及 `text-<style>-*`，覆盖 `heading-1` 到 `heading-6`、`display-1` 到 `display-3`、`body`、`large`、`label`、`supporting` 和 `code`——即核心的 Text 与 Heading 绘制的类型样式——还有 `shadow-low`、`shadow-med` 和 `shadow-high`，即核心的 Card 与 Button 绘制的高度层级。核心会补齐主题省略的每个共享 token，因此每个主题都有相同的共享成员。新增一个组会在同一个 pull request 中改变本规格、生成器和 Swift 读取方，并与第一个读取它的组件一起。
- **G6 — token 名按一条规则映射到 Swift 成员。** token 的 Swift 成员是它的组加上其余名字的小驼峰形式，两个数字之间的每个 `-` 写作 `_`：

| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Token | 成员 |
| `color-<rest>` | `color.<rest>`: `color-text-primary` → `color.textPrimary`, `color-data-blue-1` → `color.dataBlue1` |
| `spacing-<n>` | `space.s<n>`: `spacing-4` → `space.s4`, `spacing-0-5` → `space.s0_5` |
| `radius-<rest>` | `radius.<rest>`: `radius-element` → `radius.element` |
| `size-element-<rest>`, `border-width` | `size.element<Rest>`: `size-element-md` → `size.elementMd`; `size.borderWidth` |
| `text-<style>-<part>` | `font.<style>.<part>`, one `TypeStyleTokens` per style with `size`, `weight`, and `leading`: `text-body-size` → `font.body.size`, `text-heading-1-weight` → `font.heading1.weight` |
| `font-family-<rest>` | `font.family.<rest>`: `font-family-body` → `font.family.body` |
| `font-size-<rest>`, `font-weight-<rest>` | `font.size.<rest>`, `font.weight.<rest>`, with a name that starts with a digit taking `s`: `font-size-2xl` → `font.size.s2xl`, `font-size-base` → `font.size.base`, `font-weight-bold` → `font.weight.bold` |
| `shadow-<level>` | `shadow.<level>`: `shadow-low` → `shadow.low` |

字体 token 按种类分组，因为每个类型样式都是视图一起读取的多个 token：视图整体取用 `font.body`，而缺少 size、weight 或 leading 的样式会使运行失败并指明该样式。两个 token 映射到同一个成员，或某个成员部分本身是 Swift 关键字或不以字母开头，会使运行失败并给出两个 token 名。

- **G7 — 取值是带类型的，且每种转换要么精确，要么已声明。** 在应用 G1 的 `light-dark()` 规则后，每个取值在一个模式下读取。
  - 颜色是 `Color` 值。生成器读取十六进制（`#RGB`、`#RGBA`、`#RRGGBB`、`#RRGGBBAA`）；148 个 CSS 命名颜色和 `transparent`；逗号或空格语法的 `rgb()`/`rgba()` 与 `hsl()`/`hsla()`；`hwb()`；`lab()`、`lch()`、`oklab()` 和 `oklch()`；`srgb`、`srgb-linear`、`display-p3`、`a98-rgb`、`prophoto-rgb`、`rec2020`、`xyz`、`xyz-d50` 和 `xyz-d65` 中的 `color()`；上述任一空间或 `hsl`、`hwb`、`lab`、`lch`、`oklab`（默认）和 `oklch` 中的 `color-mix()`，带 `shorter`、`longer`、`increasing` 或 `decreasing` 色相；以及相对颜色（`rgb(from <color> r g b / alpha)`，每个函数同理，以及 `color(from <color> <space> …)`）。通道是一个数字、其 CSS 参考范围的百分比、`none`、相对颜色的通道关键字，或作用于这些的 `calc()`、`min()`、`max()` 或 `clamp()`；色相是一个数字或以 `deg`、`rad`、`grad` 或 `turn` 表示的角度；alpha 跟在 `/`（或第四个逗号）之后，是一个数字或百分比。逗号只在 CSS 允许处读取：在 `rgb()` 和 `hsl()`（及其 `a` 形式）中，不允许 `none`，`rgb()` 通道全为数字或全为百分比，且 `hsl()` 的饱和度和亮度为百分比。
  - 转换使用 CSS Color 4 的方程与矩阵，经由 CIE XYZ D65，D50 空间使用 Bradford 适应；`rec2020` 使用 BT.2020 分段传递曲线，与 Chromium 的绘制一致；CSS Color 4 规定 2.4 gamma。在用字面通道书写的颜色中，`rgb()` 通道钳制到 0–255；`hsl()` 与 `hwb()` 的饱和度、白度和黑度钳制在 0，`hsl()` 的饱和度和亮度钳制在 100%，与浏览器读取它们的方式一致；Lab 与 OKLab 的亮度钳制在其范围内，彩度钳制在 0。相对颜色的通道不钳制，因此它保留其来源的色域。Alpha 钳制到 0–1。`color-mix()` 遵循 CSS Color 5：省略的百分比是 100% 减去另一个（两者都省略则各为 50%），这一对被缩放为总和 100%，总和不足 100% 时结果的 alpha 乘以该总和，总和为 0% 时没有静态形式，色相在应用色相方法前对 360° 取模，`none` alpha 在预乘前取另一颜色的 alpha，通道按 alpha 预乘后插值，`none` 通道取另一颜色的类比通道（CSS Color 4 的类比分量：红、绿、蓝，包括 X、Y 和 Z；亮度，包括 `hsl()` 的亮度；色彩度；色相；以及两个对立轴；HWB 的白度和黑度没有类比分量）。输出时仍缺失的通道为 0。
  - 位于 sRGB 内的颜色（每个通道都在 0–1 的 0.000075 范围内）是 SwiftUI 自己的 `Color(.sRGB, red:green:blue:opacity:)`。位于 sRGB 之外但在 Display P3 之内的颜色是 `Color(.displayP3, red:green:blue:opacity:)`（D5）。位于 Display P3 之外的颜色是 Swift 无法精确表达的值：每个通道钳制到 Display P3，与 Chromium 的绘制一致，运行会发出警告（G15），警告以“outside Display P3; clipped to match the web”结尾。每个通道和 alpha 四舍五入到 256 个步长中最接近者，恰好居中时向上，并写为 `0`、`1`，或该步长除以 255 的精确小数（与 `n / 255` 相同的 `Double`）；包不声明自己的颜色初始化器。
  - 长度是 `CGFloat` 点：`px` × 1、`rem` 与 `em` × 16、`pt` × 4/3、`pc` × 16、`in` × 96，以及由 `in` 得到的 `cm`、`mm` 和 `Q`；作用于这些的 `calc()`、`min()`、`max()` 和 `clamp()`；`thin`、`medium` 和 `thick` 仅在 `border-width` 中分别为 1、3 和 5，其他位置不接受长度。无单位数字是点数。`em` 按 16 点根值读取并发出警告。
  - 字重（`font-weight-*`、`text-*-weight`）是 1 到 1000 的数字；`normal` 是 400，`bold` 是 700。`bolder`（700）与 `lighter`（100）按 400 读取并发出警告。
  - 行高（`text-*-leading`）是字号的倍数：数字原样，百分比 ÷ 100，长度 ÷ 同一模式下同一样式的 `text-<style>-size`（因此 `em` 按该字号计数，`1.5em` 为 1.5），保留 12 位有效数字。`normal` 是 1.2 并发出警告。
  - 字体族是 `[String]`，去掉引号，按 CSS 字体栈的顺序。
  - 阴影是 `[ShadowLayer]`，每个 `box-shadow` 层一个，按顺序，其颜色与长度顺序不限；`none` 表示没有层。投影层是 `x y [blur [spread]] color`；SwiftUI 不绘制投影扩散，因此扩散会被略去并发出警告。内阴影层是一个环，`inset 0 0 0 <width> color`，视图在其边框内绘制，与 CSS 绘制内阴影的方式一致。
  - 以下形式没有静态形式（G15）：`currentColor`；`Canvas` 之类的系统颜色；颜色通道和行高之外的百分比；视口与容器单位；字体相对单位（`ex`、`ch`、`ic`、`cap`、`lh` 及其根形式）；核心解析器未解析的 `var()`；`env()` 与 `attr()`；CSS 全局关键字；相加不同类别的 `calc()`；百分比相加为 0% 的 `color-mix()`；没有颜色的阴影层（以 `currentColor` 绘制）；以及带偏移或模糊的内阴影。这在每个 token 中都成立，包括字体族和阴影。此类取值要么采用核心的默认值，要么按 G15 所述使运行失败，其理由以“Swift has no static value”结尾。上述形式之外的取值，无论是否为合法 CSS，都会使运行失败并以“the Swift theme generator does not read this form”结尾，因此读取方缺口不会被报告为 Swift 无法容纳的值。在一个模式中存在、在另一模式中缺失的 token 会使运行失败，并给出主题、模式和 token。
- **G8 — 主题本地 token 等待按模式提供的来源。** 主题的本地 token（AST-006）只有在核心的解析器像返回共享 token 那样按模式返回它们之后才会生成；在此之前生成器不输出任何本地 token，并报告它略去的每个本地 token。生成后，每个取值以其精确的自定义属性名（AST-006 FR3、DEC-2）为键，不加第二个标识符、不读取或去掉前缀，放在按取值类型（G7）分组的映射中，分别用于浅色和深色，只由该主题携带（`Theme.neutral.local.dark.colors["--astryx-theme-neutral-color-status-fill-accent"]`）。主题未声明的名字返回 `nil`，由调用方决定绘制什么。只有为该主题编写的代码会读取它们；共享组件从不读取。
- **G9 — 组件读取带类型的成员。** 组件只通过带类型的成员（`theme.color.textPrimary`）读取 token。包内部可能存在按 token 名查找的回退，供由 wire 驱动的代码使用；它不是公共接口，也没有组件使用它。
- **G10 — 字体名映射到 SwiftUI 字体，并带有系统回退。** 读取方按顺序遍历字体族列表，使用应用可用的第一个字体族（在 iOS 上用 `UIFont(name:size:)`，在 macOS 上用 `NSFont(name:size:)`，结果不为 nil）作为 `Font.custom(_:size:relativeTo:)`，因此在 iOS 上它仍随 Dynamic Type 缩放。通用名或系统名以系统字体结束遍历：`-apple-system`、`system-ui`、`BlinkMacSystemFont` 和 `sans-serif` → `.default` 设计；`ui-monospace`、`SF Mono`、`monospace` → `.monospaced`；`ui-serif`、`serif` → `.serif`；`ui-rounded` → `.rounded`。没有可用字体族的列表绘制系统字体。库从不打包或下载字体；想要自己品牌字体的应用应自行打包并注册字体文件。
- **G11 — 原生意图有预留位置。** `Theme.native` 是一个有文档的成员，在组件读取原生意图之前为空（D3）。
- **G12 — 每个已发布主题都会被生成，产品自己的主题也可以。** 核心的默认主题以及 `packages/themes/` 下每个 `package.json` 不是 `private` 的主题包都有一个生成文件。产品通过把其主题传给 `renderSwiftTheme`，或通过包的命令（`generate:swift-ios --theme <module>#<export>`）来生成自己的主题。
- **G13 — 漂移检查覆盖带类型的表面。** 一个测试会重新生成 `Tokens.swift` 和每个已提交的主题文件，并在任何文件不同、已发布主题没有文件、或有文件没有对应的已发布主题时失败。失败信息会指明重新生成命令。
- **G14 — 生成文件目前保持提交。** Swift Package Manager 从 git 提交安装，无法运行 Node 生成器，因此在 CI 把生成的 Swift 发布到仅含 Swift 的分支或标签之前，生成文件与 Swift 源码一起提交，正如包 README 所述。

- **G15 — 每种转换要么精确，要么发出警告，要么是错误。**
  - 精确转换，包括 G7 所述的舍入，不打印任何内容。
  - 有损转换（位于 Display P3 之外、按 Chromium 绘制方式钳制的颜色；按根值读取的 `em`；按 400 读取的 `bolder` 或 `lighter`；按 1.2 读取的 `normal` 行高；被略去的投影扩散）会输出该值，并输出一条警告，指明主题、模式、token、CSS 值、输出的 Swift 值以及丢失了什么。
  - 没有静态形式的取值会使运行停止，并给出错误，指明主题、模式、token、CSS 值和原因，除非该 token 是可选的。当核心为其填充默认值时，token 就是可选的：核心的解析器在没有主题时也会返回它（`resolveThemeTokens(null, {mode})`），正如它对每个 G5 token 所做的那样。可选 token 采用核心在该模式下的默认值，经 G7 转换，并发出一条指明该默认值的警告。核心没有默认值的 token、没有静态形式的默认值，以及核心自身默认值的每个 token，都是必需的。
  - 警告在运行写入文件之后打印，每行一条，以 `warning: ` 开头。`--strict` 会把每条警告变成错误：运行打印的每行以 `error: ` 开头，不写任何文件，并以非零状态退出。产品主题（`--theme`）得到同样处理，`renderSwiftTheme` 接受 `warnings`（一个它会追加的列表）和 `strict`；不带列表调用时，它把每条警告打印到标准错误，因此丢失从不静默。token 的备注每个模式打印一次，来自失败取值的备注随它一起丢弃，因此回退的警告只指明失败和核心的默认值。

## 决策

- **D1 — 边界检查覆盖 `packages/native/` 的全部内容。** 包边界检查会扫描 `packages/native/` 下的每个文件夹，因此包内任何位置对 core 的导入都会对照 AST-082 FR16 进行检查，并且 FR16 允许的每个构建时读取都按名称列出：生成器的两个主题条目（G2）、契约生成器对 core 组件文档和内置图标名的读取，以及字符串生成器对 core 语言目录的读取。
- **D2 — 共享 token 从一开始就是类型化的。** 对于共享 token 表面，生成器输出类型化成员（G3、G6），而不是以字符串为键的字典，因此错误的 token 名无法编译，自动补全也会列出每个 token。已否决：带缺失 token 回退的字符串键，因为一个拼写错误就会发布不可见文本。主题的局部值则改为按其精确名称作为键（G8），因为 AST-006 FR3 不允许第二个标识符。
- **D3 — 原生意图通过 `defineNativeTheme` 进入一个预留槽位。** 原生视觉意图（持久的 `material`、平台条目、图标；AST-082 FR10、FR17）来自 `defineNativeTheme`，这是一个包装可移植主题的原生主题。当第一个组件读取 `material` 时，生成器取得该原生主题，从中读取被包装的可移植主题，并填入已按 OS 版本范围解析好的 `Theme.native`，因此一次调用只产生一个文件。平台条目的图标（`{systemName}` 或 `{assetName}`，AST-082 FR17）会成为 `Theme.icons` 中 `.systemName(_:)` 或 `.assetName(_:)` 形式的条目。在 `defineTheme` 内组合原生意图不在本规格范围内。

- **D4 — 增强对比度不在本规格范围内。** Core 主题只有浅色和深色模式，因此生成器不输出任何增强对比度值。core 中的对比度模式由它自己决定，位于 `packages/native/` 之外。在它出现之前，开启增强对比度时，组件用 `color.borderEmphasized` 而非 `color.border` 绘制边框和分隔线（由一个 Swift 测试检查：它将 `colorSchemeContrast` 设为 increased 并读取边框颜色）。

- **D5 — sRGB 之外的颜色保持宽色域。** iPhone 和 Mac 显示器是 Display P3，其上的浏览器会以 Display P3 绘制超出 sRGB 的主题颜色，因此 sRGB 之外的主题颜色会生成为 SwiftUI 自带的 `Color(.displayP3, …)`，外面不套任何 Astryx 初始化器，只有 Display P3 之外的颜色才被裁剪，按浏览器的绘制方式处理，并给出警告（G15）。已否决：把每种颜色都映射到 sRGB，因为那样一来，同一个设备上的品牌色在 Swift 中会比在 Web 上显得更暗淡。

## 当前状态

- `packages/native/apple/` 是一个 Swift 包，包含 `AstryxNative` 产品（生成的契约类型）和 `Astryx` 产品（SwiftUI 视图）。
- 生成的主题用 SwiftUI 自带的初始化器书写每种颜色；`Astryx` 模块不添加任何 `Color` 初始化器。
- 生成器写出类型化的 `Tokens.swift`，并为 core 的默认值以及每个已发布的主题包（`Theme.default`、`Theme.neutral` 等）各写一个主题文件，放在 `apple/Sources/Astryx/Theme/Generated/` 下。字体 token 按类型样式（`font.body`、`font.code`、`font.display1`–`3`、`font.heading1`–`6`、`font.label`、`font.large`、`font.supporting`）和按尺度（`font.family`、`font.size`、`font.weight`）分组。
- Core 的 `resolveThemeTokens` 按模式返回共享 token，不返回局部 token；neutral 声明局部 token，以 `light-dark(…)` 字符串存储。
- 已发布的主题包：butter、chocolate、gothic、matcha、neutral、stone、y2k（probe 是私有的）。它们的原始值在 G5 分组（组件样式）之外使用 `oklch()` 和 `color-mix()`，neutral 的投影使用带内嵌描边环的 `oklch()`，而 `color-mix()` 只在 `--color-syntax-added` 和 `--color-syntax-removed` 中出现在分组内。
- Core 的解析器会替换 token 之间的 `var()` 引用，并对它解析出的颜色求值 `color-mix(in srgb, …)`；生成器自行转换其余每种 G7 形式。
- 每个已发布的主题都能无警告地生成，且其中每种颜色都在 sRGB 之内。
