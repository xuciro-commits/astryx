## Intent

在手机上打字的人能看见自己正在输入的字段以及它周围的区域，它们都在屏幕键盘之上，并且字段获得焦点时页面不会猛然晃动。每个响应键盘的区域都以相同的方式测量键盘，并让页面保持不动，因此键盘在 sheet、聊天输入框或搜索字段中的行为都一致。Core 输入组件与键盘协同工作：每个会唤出键盘的 Core 字段都把自身保持在键盘之上——无论是在页面中、在 Core 宿主中，还是在应用停靠到 viewport 底边的栏中，应用都无需开启任何东西。

## Non-goals

- 层几何：Popover 及其他锚点模式的层如何保持在键盘之上，属于 `spec:AST-059`。
- 硬件键盘访问与焦点顺序，由 `spec:AST-025`、`spec:AST-020` 和组件记录拥有。
- 随键盘移动某区域的动画的曲线或时序，超出 FR3 的同步与 FR8 的限制之外；在减少动态下它遵循 `design:reduced-motion`。
- 应用的 viewport `<meta>` 元素，它由应用拥有。
- `@astryxdesign/native`，那里适用平台自身的键盘避让（`spec:AST-082` FR11）。
- 等价的内部实现只要满足本契约，仍然有效。

## Requirements

- **FR1 — 每个组件使用同一个键盘高度。** 每个相对于屏幕键盘进行定位、尺寸计算或关闭的 Core 和 Lab 组件，都在同一时刻响应同一个键盘高度（FR2），包括 BottomSheet、聊天输入框、放在底部的搜索字段、标签栏搜索、拖拽关闭，以及任何键盘布局引导（keyboard layout guide），因此没有两个组件会对键盘所在位置产生分歧。`architecture:react-component-runtime` INV11 拥有该高度的唯一来源，以及 Core 之外的组件如何与其保持一致。
- **FR2 — 平移或缩放无法破坏的高度。** 键盘高度等于布局 viewport 高度减去视觉 viewport 高度，再乘以视觉 viewport 的缩放比例，单位为 CSS 像素。没有显示键盘时为 0，包括页面上正在进行双指缩放时。页面平移或视觉 viewport 偏移是一项需要还原的平移（FR4），绝不会被当作更小的键盘。
- **FR3 — 键盘高度保持内部使用，并保持布局正确。** 没有任何公共 CSS 自定义属性、导出或 prop 暴露键盘高度。每个组件在自己的元素上应用它，例如底部偏移、内边距或最大高度，因此即使没有动画运行，布局也是正确的：聊天输入框、放在底部的搜索字段和标签栏搜索由它来定位，而完全展开的 sheet 用它扩展自身的滚动范围。FR9 的停靠跟随是唯一的例外：Core 按 FR9 的规定移动应用的停靠栏。该值如何进入样式由 `architecture:react-component-runtime` INV11 决定。键盘的运动层叠放在该布局之上，因此布局从不依赖它；FR8 在适用之处要求这一点。当区域跟随它移动时，例如输入框、滚动视图和头部，它们都沿同一运动同步移动到静止值，且没有逐帧布局工作，每个区域只把静止值提交一次到布局，形式为偏移、内边距或占位元素（spacer），因此不会有内容被隐藏或无法滚动。该运动如何共享由 `architecture:react-component-runtime` INV11 决定；没有公共 API 或 CSS 自定义属性暴露它。在 iOS 上的 Safari 中——它只在键盘完全落下后才报告键盘——一个完全展开的 sheet，其字段把焦点让给一个既不会唤出键盘、也不会在键盘位置唤出选择器的控件时，会保持其键盘布局，并让内容按键盘自身隐藏所播放的运动（UIKit 的键盘弹簧），从失焦开始，以 translate 的形式移动到其静止滚动位置，且没有逐帧 JavaScript。一旦视觉 viewport 恢复，布局撤销、translate 清除在一次提交中完成，因此没有任何东西移动。在减少动态下不产生任何位移，且该变化遵循 `design:reduced-motion` DR2。
- **FR4 — 焦点从不让页面平移。** 进入键盘感知区域内部文本输入控件的每条路径——包括点击、键盘的上一个和下一个按钮、Tab，以及程序化聚焦——都在不触发浏览器滚动文档的情况下传递焦点，并由该区域用自己的滚动容器把控件带入视野。当键盘的 Done 按钮结束输入时，焦点移动到该区域，以便下一次点击以相同方式处理。在页面被滚动锁定时仍然发生的文档滚动，例如返回应用时，会在同一帧内还原。
- **FR5 — 移动区域会关闭键盘。** 当持有焦点控件的区域开始移动时，例如在高度之间被拖动的 sheet、拖拽关闭或关闭动作，该控件会失焦，从而关闭键盘，并且该区域保持其键盘布局，直到视觉 viewport 恢复，因此内容不会在移动的第一帧跳动。
- **FR6 — 能力检测。** 键盘处理只在视觉 viewport 因键盘而收缩、而布局 viewport 保持其高度的地方起作用。它从平台的 viewport 和键盘能力来检测这一点，绝不从 user agent 检测（`spec:AST-013` FR6）。在浏览器还报告屏幕键盘几何信息的地方，例如 Android 上的 Chrome，高度在那里同样来自 FR2，而 FR8 决定区域如何跟随键盘——在任何显示屏幕键盘的设备上都是如此；提供该报告但不显示屏幕键盘的浏览器读到 0。不是安全上下文的页面得不到这样的报告，因此 FR8 在那里不适用。
- **FR7 — 仅限顶层文档。** 在 iframe 内部，键盘打开时 frame 的视觉 viewport 不会改变，因此那里的键盘高度为 0，什么都不会变化。本记录的行为和证据来自顶层文档。
- **FR8 — 报告键盘的浏览器平滑跟随键盘。** 在自身报告屏幕键盘几何信息的浏览器中，例如 Android 上的 Chrome，键盘高度在那里同样来自 FR2 的视觉 viewport 测量（DEC-4），Core 的键盘感知区域在显示和隐藏时都跟随键盘：它们随键盘的滑动移动，在已测量的键盘上处于其一帧之内，没有一步跳跃，没有区域被留在键盘之下，没有逐帧 JavaScript，静止时只有一次布局提交（FR3）。有两个例外适用（DEC-6）。在 Android 上的 Chrome 中，在键盘首次报告时，内容会在一个帧内被放置好，使焦点字段的底部正好位于键盘顶部之上，然后跟随键盘滑动的其余部分。如果报告后约 100–170 ms 字段仍在键盘之下，Chrome 会自行平移页面，因此不能依赖滑动。在 Android 上的 Chrome 中，页面上没有任何东西能预测的隐藏（例如 Back）会在键盘滑动进行到中途时被报告；内容从那一次报告开始向下跟随。在减少动态下，没有任何东西随键盘移动，且该变化遵循 `design:reduced-motion` DR2，即在触摸屏上做交叉淡化。Lab 区域只提交静止值，不跟随（`architecture:react-component-runtime` INV11）。Astryx 从不覆盖应用自身的 viewport 设置。在应用设置 `interactive-widget=resizes-content` 的地方——Astryx 记录它但不设置它——Android 上的 Chrome 会随键盘收缩布局 viewport，因此 FR2 读到 0：键盘感知字段在那里的键盘高度为 0，且不跟随，因为浏览器已经腾出了空间。在其他所有地方，键盘感知区域跟随视觉 viewport 高度（DEC-4）。没有键盘几何 API、只收缩其视觉 viewport 的 Android 浏览器，例如 Firefox for Android，在 FR6 下获得 FR2–FR5。
- **FR9 — 每个唤出键盘的 Core 字段都保持在键盘之上。** 当屏幕键盘打开时，获得焦点的 Core 文本输入字段会保持在键盘之上可见，应用无需做任何事——无论它渲染在页面的滚动内容中、在 Core 宿主（例如 sheet 或聊天输入框的停靠区）中，还是在应用停靠到 viewport 底边且自身未设置 `translate` 的固定栏中。位于滚动内容或 Core 宿主中的字段与键盘顶边保持 10 CSS px 的间距，这正是 `spec:AST-059` FR9 在层之下保留的间距；位于应用停靠栏中的字段随该栏一起移动，栏的底部与键盘顶边相接。Core 不移动任何其他固定容器（浮在底边之上的、自行设置 `translate` 的，或占满整个 viewport 的）；由应用为其定位。键盘顶部即 FR2 的高度。对于 Core 显示或移动的字段，页面绝不会被平移或位移。在 FR9 留给应用处理的固定容器内部，字段与该容器之间若有滚动容器，则该字段遵循滚动内容规则：由最近的滚动容器显示它，页面不被平移。只有当字段与该容器之间没有滚动容器时，才保留浏览器自身的聚焦显示行为，而在 Safari 中这可能平移页面。
  - **滚动内容。** 滚动内容中的字段由最近的滚动容器（包括文档在内）在键盘尺寸被报告的同一下帧内滚动到位。当该滚动容器无法滚动足够远时，它在键盘显示期间于末端获得缺失的滚动范围，并在键盘隐藏时失去该范围。其他任何内容都不移动。
  - **停靠容器。** 停靠在 viewport 底部的字段——位于底部栏、固定工具栏或 sheet 中——跟随键盘：其停靠容器在键盘打开时上移、在关闭时下移，在适用之处采用 FR8 的跟随（DEC-2），在其他地方则跟随视觉 viewport 高度（FR2），例如 iOS 上的 Safari。Core 宿主通过在自己的元素上应用键盘高度来跟随（FR3），其内部的字段不会被再次移动。
  - **应用拥有的停靠容器。** 应用拥有的容器在同时满足以下条件时也跟随：采用固定定位、不占满 viewport，并且处于停靠状态——其布局盒（在任何变换之前）位于 viewport 的底边。对于绘制盒移动后无法容纳于键盘上方空间的停靠容器，例如全高侧边抽屉或固定头部下方的窗格，由字段来处理：如果有滚动容器持有该字段，则通过该滚动容器显示字段，容器不移动；如果没有滚动容器持有它，则容器只移动到焦点字段避开键盘所需的距离，绝不超过容器自身的重叠量，因此即使容器的顶部移出屏幕，字段仍保持可见。能容纳的停靠容器上移的距离，是从其绘制后的底边（在应用自身施加的任何抬升之后）到键盘顶边的距离；该距离在每次键盘报告之后测量，包括焦点仍在该栏中而键盘高度发生变化的情形，也在每次焦点移动之后测量，且在页面自身的监听器运行完毕之后进行。因此，应用已经抬升到键盘处的栏不会被再次抬升；应用只抬升了一部分的栏，移动剩下的部分；原地不动的栏则移动全部重叠量。对于应用正在用 CSS transition 或 animation 移动的栏（在 Core 测量时正运行于其位置上），Core 不予处理，因此该栏绝不会被抬升两次。Core 看不到应用每帧通过脚本移动的栏；通过脚本抬升其栏的应用要用自己的 `translate` 为其定位——Core 绝不移动该属性——以保持其不被遮挡。该移动会叠加到应用设置的任何变换之上。若某栏自身的计算值 `translate`（即应用设置的值，而非 Core 的移动）不是 `none`，例如用 `translate: -50% 0` 居中的栏，则不会被移动。该栏的静止状态就是这次移动，而不是对其布局的更改；一旦字段失去焦点后键盘隐藏，或字段卸载，该移动就撤销。Core 不更改应用元素上的其他任何东西。这是 FR3 的唯一例外（DEC-5）。
  - **无 API。** 没有 prop、选项、context 或其他公共 API 可以开启、关闭或调节它，对于上述位置中的字段，应用无需做任何事即可获得该行为。字段获得焦点的每条路径（FR4）都得到相同的行为。
  - **覆盖的字段：**
    - TextInput、TextArea 和 NumberInput；
    - DateInput、DateTimeInput 和 TimeInput 的可输入字段，在所有会渲染此类字段的呈现形式中；
    - Typeahead 和 Tokenizer 的输入框（由 BaseTypeahead 渲染），以及 Tokenizer 的 sheet 搜索字段；
    - Selector 和 MultiSelector 的搜索行；
    - PowerSearch 的查询输入框、其值编辑器的文本字段和数字字段，以及其 sheet 流程的搜索字段和值字段；
    - CommandPalette 的搜索输入框；
    - ChatComposer 的输入框。

之后新增的、会唤出键盘的 Core 字段也受同一规则覆盖。不唤出键盘的字段则不在此列：没有输入模式的只读触摸选择器字段、原生日期或时间选择器、DateRangeInput 的触发元素、FileInput、Slider，以及 Selector 或 ComplexSelector 的触发元素。Lab 字段遵循 INV11 对 Core 之外组件的规则。

### Platform support

- 支持的功能/引擎下限：该包支持的浏览器（`spec:AST-013` FR3）。FR2–FR5 适用于 iOS 上的 Safari（在浏览器中以及作为主屏幕应用），也适用于 Firefox for Android；FR8 的跟随适用于浏览器自身报告键盘的任何地方，例如 Android 上的 Chrome。
- 不支持的行为：没有屏幕键盘，或不支持视觉 viewport 时，键盘高度为 0，什么都不会变化。服务端渲染期间它不渲染任何内容，也不读取任何 viewport。
- 浏览器证据：iOS 上的 Safari（在 iOS 模拟器中，或在设备上并处于顶层文档中）证实 FR2–FR5 中关于 iOS 的断言；带 Gboard 的 Android 模拟器中的 Chrome on Android 证实 FR8；模拟器中的 Firefox for Android 证实那里的 FR2–FR5（`spec:AST-013` FR10）；DOM 与视觉 viewport 测试证实 FR1–FR7 的其余部分。顶层文档中的模拟器与仿真器证据是合并的门槛。Android 证据是在确切 head 上的仿真器证据，动画需分别在正常速率和移除状态下测试，另加慢速设备配置文件，且不做人工设备检查（`spec:AST-094` DEC-27）。在键盘模块随发行版发布之前，需要在实际 iPhone 上通过，包括手机真实的刷新时序（DEC-3）。

## Current-state impact

- BottomSheet 的键盘 hook 位于 Core 的键盘模块 `packages/core/src/keyboard/` 中，即 `architecture:react-component-runtime` INV11 所指的唯一来源。它为完全展开的 Tall sheet 实现 FR2、FR4 和 FR5，按能力做判断（FR6），并通过作用于 sheet 自身元素的函数式样式应用该高度（FR3）。BottomSheet 使用它（`component:BottomSheet`）。
- `main` 上没有其他组件测量键盘；BaseTypeahead 读取视觉 viewport 高度仅用于确定其列表尺寸（Gap 4）。之后响应键盘的组件使用同一高度（FR1）。
- FR9 覆盖的每个字段都获得它在 `main` 上缺少的键盘行为（Gap 2–11）；输入组件族引用了 FR9（`family:input-fields` FR13）。
- 拥有自己的固定底部栏的应用：键盘打开时原地不动的栏在 FR9 下跟随键盘。应用已经随键盘移动的栏在两种情形下保持原样：应用正用 CSS transition 或 animation 移动它，且在 Core 测量时仍在运行——这种情况 Core 留给应用处理；以及应用通过脚本用自己的 `translate` 移动它——这种情况 Core 绝不移动。应用已经抬升过的栏按其绘制状态测量，因此 Core 不对其做任何移动；应用只抬升了一部分的栏（没有 CSS 运动在运行）由 Core 移动剩下的部分，并叠加在应用自身的变换之上。应用在 Core 测量之后才开始的 CSS 抬升可能被抬升两次；应用每帧通过脚本在 `transform` 上驱动的抬升也是如此，Core 看不到后者。不需要 opt-out API。
- 用 `translate` 定位的栏，以及浮在底边之上的固定容器，都不跟随：Core 让它们留在应用放置的位置。其中有滚动容器持有的字段仍由该滚动容器显示；字段与其容器之间没有滚动容器时，字段可能留在键盘之下。希望获得跟随的应用应把栏停靠到 viewport 底边，并用 `transform` 定位，或不设置 `translate`（后续工作）。过高而无法容纳于键盘上方的停靠容器，例如全高侧边抽屉或固定头部下方的窗格，在有滚动容器持有字段时不移动，否则只移动到焦点字段所需的距离。
- `architecture:react-component-runtime` INV11 允许 FR9 的停靠跟随：Core 在应用停靠的固定容器上写入并移除一个 `translate`（该容器自身的 `translate` 为 `none`），其值等于从其绘制后的底部到键盘顶部的距离，并且不在应用元素上做其他任何改动（DEC-5）。
- 层的上限没有把键盘计算在内：`spec:AST-059` 拥有层几何，让 Popover 及其他锚点模式的层保持在键盘之上，是对该记录的修订，并消费此高度。
- 键盘模块的高度包含 FR2 的缩放项，因此双指缩放后的页面不会被误读为键盘。
- 在能够测量键盘的地方，该 hook 在粗指针（coarse pointer）下接管焦点；没有任何 user-agent 检查来把关。在 FR8 下，Chrome on Android 中完全展开的 Tall sheet 保留 `BottomSheet.doc.mjs` 记录的键盘适配，并随键盘移动，因此没有使用方失去行为，也不适用破坏性变更；`BottomSheet.doc.mjs` 说明了各平台的行为。Firefox for Android 获得 FR2–FR5。
- 没有公共 API 暴露键盘高度，FR3 保持这一状态。
- 使用方文档新增 Android 的 viewport 设置（FR8）。

### Implementation gaps

在 `main` 上，没有任何被覆盖的字段满足 FR9。以下每个缺口都仍然开放。

- **Gap 1 — 键盘模块。** 部分满足：键盘模块（`packages/core/src/keyboard/`）测量键盘、防止焦点平移页面，并把获得焦点的字段保持在键盘之上：它跟随停靠容器、滚动字段最近的滚动容器，并接管首次点击。BottomSheet 的 Tall sheet 和 ChatLayout 的停靠区读取它。目前没有其他被覆盖的字段读取它（Gap 2–8）。
- **Gap 2 — TextInput、TextArea 和 NumberInput。** 它们都没有键盘焦点处理。在页面中，只有浏览器自身的显示滚动会把字段带入视野，且没有任何证据表明它会保持在键盘之上。
- **Gap 3 — DateInput、DateTimeInput 和 TimeInput 的可输入字段。** 没有键盘处理。它们的触摸选择器字段是只读的、没有输入模式，也不会唤出键盘，因此不在 FR9 的范围内。
- **Gap 4 — Typeahead 和 Tokenizer 的输入框。** BaseTypeahead 的输入框没有键盘处理。BaseTypeahead 自行读取视觉 viewport 高度来确定其列表尺寸，绕过了键盘模块。
- **Gap 5 — Tokenizer 的 sheet 搜索字段。** 部分满足：该字段位于 Tall sheet 中，因此 BottomSheet 的 hook 只在 sheet 完全展开时覆盖它。部分展开的 sheet 得不到任何处理。
- **Gap 6 — Selector 和 MultiSelector 的搜索行。** 在粗指针下，该行位于 `hug` BottomSheet 中，BottomSheet 的 hook 不覆盖它，而它自身也没有键盘处理。
- **Gap 7 — PowerSearch。** 在紧凑的粗指针屏幕上，其默认呈现形式是它的 sheet 流程（`component:PowerSearch` DEC-3）：Tall 底部 sheet，BottomSheet 的 hook 只在 sheet 完全展开时覆盖其中的搜索字段和值字段，正如 Gap 5 对 Tokenizer 所述。它的查询输入框（Gap 4）及其 popover 值编辑器的文本字段和数字字段，只有使用 `presentation="popover"` 时才在那里渲染，而在其他所有地方都是默认渲染；它们没有键盘处理。让 popover 自身保持在键盘之上属于 `spec:AST-059` 的范围。
- **Gap 8 — CommandPalette 的搜索输入框。** 它位于 Dialog 中，没有键盘处理。
- **Gap 10 — 应用构建的固定宿主中的字段。** 位于应用自身的固定或粘性底部栏中、固定 Toolbar 中，或位于并非完全展开的 Tall sheet 的 BottomSheet 中的被覆盖字段，没有任何处理能让它保持在键盘之上。
- **Gap 11 — 缺失的滚动范围。** 部分满足：键盘模块把应用停靠的固定容器移动到键盘顶部，并在键盘被报告的那一帧把字段最近的滚动容器滚动到使其位于键盘上方 10 CSS px 的位置（`packages/core/src/keyboard/keyboardTarget.ts`），但目前没有哪个被覆盖的字段使用它（Gap 2）。没有字段在其滚动容器末端补上缺失的滚动范围；在某个字段这样做之前，没有可滚动内容的元素不算作滚动容器（该字段保留浏览器自身的显示行为）。BottomSheet 的内缩仅作用于其自身的 sheet。
- **Gap 12 — Firefox for Android 中完全展开的 sheet 的隐藏。** Firefox for Android 不报告键盘滑动，因此 sheet 走与 iOS 上的 Safari 相同的路径（`packages/core/src/keyboard/useMobileKeyboard.ts`）。但 Firefox 只在隐藏结束时报告一次键盘隐藏。sheet 的内容在该报告时于一帧内移动，而不是从失焦开始跟随（FR3）。

### Follow-up

跟随浮动栏，以及与应用自身的 `translate` 组合，是 FR9 之外的开放工作。FR9 把浮在底边之上的固定容器，或自行设置 `translate` 的固定容器，留给应用处理。

## Decision log

### DEC-1 — One keyboard height for every component, measured so a pan cannot corrupt it

**Reference:** `spec:AST-099/DEC-1`

**Decider:** `cixzhang`, `2026-10-24`

BottomSheet 的键盘 hook 已经在每条焦点路径上让固定表面保持不动，并测量键盘使页面平移无法将其缩小，而这两点正是让字段留在键盘之下的两类失败。把它做成 Core 组件所使用的唯一来源，以及 Core 之外的组件据以测量的定义，可以避免各组件各自漂移出不同的测量结果。通过 StyleX 函数式样式应用该 hook 的高度，既能不加动画就保持布局正确，又能让共享 API 保持受约束：高度留在内部，此后需要它的应用会得到一次经过考量的公共 API 决策，而不是一个它已开始依赖的变量。

动画叠加在正确的布局之上，绝不让布局变得正确。

已否决：每个组件按自己的规则测量键盘并预测其运动，这会在任何未被认领的焦点路径上平移并产生分歧；为高度提供公共 CSS 自定义属性，而由 hook 派生的值并不需要它。

### DEC-2 — Chrome on Android rides the keyboard smoothly

**Reference:** `spec:AST-099/DEC-2`

**Decider:** `cixzhang`, `2026-10-24`

Android 上的用户应当看到与 iPhone 上同样平滑的键盘运动：一个在键盘完成移动后才跳动的表面，或一个在键盘移动时仍停在它下面的表面，都让人感觉是坏的。因此，能感知键盘的表面在 Chrome on Android 上也随键盘的滑入与滑出而跟随，依据 visual viewport 的高度（DEC-4），而应用自己的 viewport 设置仍然说了算：当应用设置 `interactive-widget=resizes-content` 时，浏览器已经让出了空间，这些表面便无可跟随。机制留给实现决定；本记录只陈述运动及其限制。

已否决：在键盘稳定后跳动的一步式重排；以及覆盖应用的 viewport 设置。

### DEC-3 — Simulators gate merge; a physical iPhone gates release

**Reference:** `spec:AST-099/DEC-3`

**Decider:** `cixzhang`, `2026-10-24`

顶层文档中的模拟器与仿真器证据，加上 Android 仿真器上的 Gboard，足以合并键盘相关的工作，因此这项工作不受硬件阻塞；而在键盘模块随版本发布之前，必须有一台物理 iPhone 上的通过，包括该手机真实的刷新时序，因为键盘时序与 viewport 行为在真实设备上有所不同。Android 方面的结论以仿真器证据为依据，无需人工设备检查（`spec:AST-094` DEC-27）。

已否决：把物理设备作为合并门槛，这会因硬件而阻塞工作；以及把物理设备作为可选后续，这可能让未经测试的键盘行为发布出去。

### DEC-4 — The keyboard height comes from the visual viewport in every browser

**Reference:** `spec:AST-099/DEC-4`

**Decider:** `cixzhang`, `2026-10-25`

在 Chrome on Android 中，visual viewport 会随着键盘开始滑动而为键盘缩小，因此 FR2 的测量能及时到达页面，让各表面在一帧之内加入滑动，而读取它不会改变页面上的任何东西。浏览器自身的键盘几何报告需要页面覆盖在键盘之上，到达更晚也更不稳定，并且在 Chromium 中会在键盘所在的那一帧隐藏底部工具栏，从而移动布局。在每个浏览器中使用同一种测量，也保持了 FR1 的单一高度。

已否决：把浏览器的键盘几何报告作为高度，它到达更晚、更不稳定，并且会移动布局。

### DEC-5 — Core inputs work with the keyboard, with no prop, and docked fields ride it

**Reference:** `spec:AST-099/DEC-5`

**Decider:** `cixzhang`, `2026-11-03`

Core 输入能与屏幕键盘配合工作。在触摸设备上，让获得焦点的字段保持在键盘之上，是所有会唤起键盘的 Core 字段的预期默认行为，而不是附加功能。该行为是每个此类字段内部的，因此没有应用需要记得开启它，也不会为此增加公共 API。

每个 Core 字段都可以跟随键盘，这一点也在 2026-11-03 决定：停靠在视口底部的字段会随键盘把自己的停靠容器上移并复位，即使该容器由应用拥有，因为一个跳动或藏在键盘之下的停靠栏让人感觉是坏的。这是 FR3 关于组件只移动自身元素这一规则的唯一例外，`architecture:react-component-runtime` INV11 允许它。

负责人在 2026-11-03 确定了范围。应用拥有的容器只在其为固定定位、且停靠到视口下边缘时才移动；填满视口的固定容器永不移动。Core 显现或移动的页面内容永不被平移或 translate；在固定容器内部，有些情形 FR9 留给应用处理（浮于下边缘之上的容器、设置自有 `translate` 的容器，或全视口容器），由滚动容器持有的字段由该滚动容器显现，只有字段与其容器之间没有滚动容器时，才保留浏览器自身的焦点显现，而这在 Safari 中可能平移页面。滚动内容中的字段由最近的滚动容器滚到位置，文档也算在内，停在其上方 10 CSS px，并与键盘被报告处于同一帧。靠近滚动容器末端的字段，会在键盘显示期间于该滚动容器末端获得缺失的空间作为滚动范围。只有停靠容器会被 translate。容器的布局盒在任何 transform 之前位于视口下边缘时，该容器即为停靠，它按从其绘制后的底边（在应用自身的抬升之后）到键盘顶部的距离移动，因此应用已经抬升的栏不会被抬升两次，也不需要选择退出。当应用正以 CSS transition 或 animation 移动某个栏、且该动效在 Core 测量时仍在运行，Core 就不动它，也永不移动带自有 `translate` 的栏；应用在 Core 测量之后才开始的 CSS 抬升可能被抬升两次，因此用脚本抬升栏的应用会以自己的 `translate` 为其定位，以保持避让。浮于下边缘之上、或以自有 `translate` 自行定位的栏，留给应用处理。过高的停靠容器在移动后无法容纳于键盘之上，例如全高侧边抽屉或固定页眉下方的窗格：当有滚动容器持有字段时它不移动，而由该滚动容器显现字段；当没有滚动容器持有时，容器只移动到获得焦点的字段让开键盘所需的程度，绝不超过其自身的重叠量，因此即使容器的顶部离开屏幕，字段仍留在视野中。

已否决：opt-in prop 或逐组件的键盘处理；把应用的停靠栏留给浏览器的显现机制。

### DEC-6 — In Chrome on Android, the focused field is placed above the keyboard at its first report

**Reference:** `spec:AST-099/DEC-6`

**Decider:** `cixzhang`, `2026-11-03`

在 Chrome on Android 中，键盘首次报告时，内容在一帧内完成放置，使获得焦点的字段的底边正好位于键盘顶部之上，随后内容跟随键盘滑动的其余部分。如果在报告后约 100–170 ms 时获得焦点的字段仍被绘制在键盘之下，Chrome 会自己平移页面，幅度为键盘的整个高度。在该平移结束之前页面得不到帧，因此平移只能以瞬跳的方式复原。放置发生期间，Chrome 会把键盘顶部以下的区域变空白。在装有 Gboard 的 Android 仿真器上，一帧内放置的做法在 12 次显示中没有出现平移，包括在 4× CPU 和把跟随放慢 5× 的情况下。在 50 ms 内到达键盘顶部的滑动，在 8 次显示中有 1 次出现平移，在 4× CPU 下 4 次中有 1 次。负责人团队的并排录屏显示，放置做法在 5 次中 0 次出现平移，而滑动在 8 次中有 7 次。

在 Chrome on Android 中，页面上没有任何东西能预测的隐藏，例如“返回”，会在键盘滑动的中途被报告；内容从该报告处向下跟随。

已否决：快速滑动，当页面卡顿时 Chrome 的平移仍会超过它；VirtualKeyboard 覆盖设置，它会改变 DEC-4 的测量来源以及页面的布局。
