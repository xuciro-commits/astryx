# App themes system spec

## Intent

构建者——无论是人还是编码 agent——想要一个使用一个或多个主题的应用：一个第一方主题、一个来自已安装集成包的主题，或一个应用自己创建的主题。他们想要找到主题、添加主题、选择默认主题、让用户在运行时在主题之间切换，并知道这套设置是正确的。

应用以源码形式复制的主题不再接收其所有者的更新，失去其包身份，并且必须由应用重新构建。它还会失去其包在它旁边加载的任何样式表，例如字体样式表，因此可能在没有报错的情况下以回退字体渲染。使用多个主题的应用需要一个列出它们的地方、一种在它们之间切换的方式，以及一项证明设置正确的检查。

本记录拥有应用如何通过 CLI 查找、声明、导入、切换和检查其主题。规则对每个主题都相同：应用通过导入主题的已构建形式并将其传递给 `Theme` 来使用主题，并通过扩展该主题来自定义它。复制主题的源码是明确的作者分叉。`theme add` 通过两个生命周期阶段达到该规则（FR12）：一个可选的导入在其已弃用的复制默认值旁发布，而该导入在一个由所有者安排的次版本中成为默认值。`architecture:theme-application` 已经支持在一个页面上使用多个已构建主题，因为已构建主题的 CSS 作用域限定于主题的名称，而切换只改变活动身份。`spec:AST-017` 拥有兼容性、生命周期和响应字段，`spec:AST-042` 拥有命令准入，`spec:AST-040` 拥有对使用方文件的写入，`architecture:cli-surface` 的 INV19 和 INV24 拥有集成项如何被描述。

## Non-goals

- 用于切换主题并保存用户选择的 Core 组件。生成的模块为应用提供了切换器所需的一切；Core 组件是一项单独的组件决策。
- 延迟加载主题样式表。
- 查找未安装的主题。
- 改变主题的创作、编译或在运行时应用的方式。
- 合并或重命名第一方主题包。
- 让主题源码归 CLI 所有。生成的模块只导入并列出应用的主题；每个主题的源码仍归其作者所有。
- 字体样式表如何提供其字体。包中的字体文件和字体服务都满足 FR7；由包自行选择。
- 读取 0.6 主题目录（`themes/manifest.json`）。包使用类型化描述符描述主题，任何根目录都不持有目录文件（`architecture:cli-surface` INV24），并且没有任何主题命令读取它。
- 等价的内部实现在满足本契约时仍然有效。生成模块的精确文本、发现代码以及回执字段顺序属于实现。

## Requirements

- **FR1 — 导入主题会将其添加到应用。** `theme add <slug> --import [--package <package>]` 必须通过将主题添加到应用的主题记录（FR3）并重新生成应用的主题模块（FR2），使该主题成为应用的一部分。它不得将主题源码复制到项目中，也不得编辑应用代码。导入一个已添加的主题会重新生成模块，并报告没有变更。导入一个已从不同所有者添加的 slug 会将其切换到新所有者并报告该变更。属于复制路径（FR12）的目标路径或 `--overwrite` 与 `--import` 一起使用时，必须在写入前失败。`theme add`、`theme list` 和 `theme eject` 的 `--package` 选项接受主题包的任一名称：提供它的包，或应用从中导入它的包，即记录中保存的那个。
- **FR2 — 一个生成的 theme 模块。** CLI 必须维护一个模块，它导入每个已添加主题的已构建模块和样式表。它导出 `themes`（每个已添加主题，以 slug 为键）和 `defaultThemeSlug`（默认 slug）；TypeScript 模块还导出类型 `ThemeSlug`，即已添加 slug 的联合。这些导出是模块的公共契约，其主题记录（FR3）不属于其中。模块带有生成标记，CLI 会重新生成整个模块而不是编辑它（`spec:AST-040/FR5`）。当项目使用 TypeScript 时，模块是 TypeScript，否则是 JavaScript。它有一个固定的位置：项目有 `src` 文件夹时位于项目 `src` 文件夹中的 `astryx-themes.ts` 或 `astryx-themes.js`，否则位于项目根目录。已存在的模块保持原位，即使项目新增或失去 `src` 文件夹。没有配置可选择该位置（`spec:AST-017/FR19`）。当该位置存放着 CLI 未生成的文件，或存在多于一个生成的 theme 模块时，命令必须在写入前失败并指明这些文件。
- **FR3 — 模块就是应用的主题记录。** 主题模块以 CLI 无需运行该模块即可读取的形式，记录每个已添加主题的 slug 和所有者、包名或项目的本地主题根目录，以及默认 slug。执行导入的 `theme add`、`theme remove` 和 `theme use` 读取该记录、修改它并重新生成模块。默认值必须是已添加主题之一。没有 `package.json` 字段、配置键或环境变量记录或选择应用的主题（`spec:AST-017/FR14`、`spec:AST-017/FR19`）。在有主题模块的项目中，读取应用默认主题的命令读取模块的记录；在没有主题模块的项目中，现有的 `astryx.theme` 字段保留其已发布含义。CLI 不读取 `ASTRYX_THEME`（DEC-7）。
- **FR4 — 集合与默认值由命令管理。** `theme remove <slug>` 从应用中移除一个主题，`theme use <slug>` 使一个已添加主题成为默认主题。移除默认主题必须失败，并指明使用另一个已添加主题的 `theme use`，或在它是唯一主题时指明 `theme list`；对未添加的主题执行 `theme use` 或 `theme remove` 必须失败，并在存在该 slug 的可用主题时指明导入命令，或在不存在时指明 `theme list`。每个命令都会重新生成模块（FR2）。
- **FR5 — 一份回执描述应用的主题。** 执行导入的 `theme add`、`theme remove` 和 `theme use` 必须返回 `theme.app` 响应：每个已添加主题及其 slug、所有者、它所导入的模块和样式表；默认 slug；模块路径；以及命令所做的变更。文本输出显示相同的事实。项目中的首次导入还会显示一次性接线：从模块导入 `themes` 和 `defaultThemeSlug`，并将 `themes[defaultThemeSlug]` 传递给 `Theme`。已构建模块仅导出一个颜色模式（`colorModes`）的主题携带该 `mode`，模块在 `themeModes` 中列出它，接线将所选主题的模式传递给 `Theme`；首次向已接线的应用添加 `themeModes` 的变更会标记 `wireModes` 并显示该接线。
- **FR6 — eject 就是作者分叉。** `theme eject <slug> [path] [--overwrite] [--package <package>]` 必须以与复制版 `theme add` 完全相同的方式（FR12），将主题的完整源码目录复制到项目中，并具有相同的路径安全性和回滚。它还必须复制主题的同名主干描述符（`architecture:cli-surface` INV24），使被 eject 的主题成为可发现的本地主题（FR8）。副本不得声称自身由主题的原始所有者维护。`--overwrite` 会替换同一主题早期分叉的文件。Eject 必须拒绝这样的目标文件夹：其中存放着主题编辑器生成的主题（文件夹 `<slug>/` 存放 `<slug>.settings.json`），或另一个主题的描述符或入口；即使带 `--overwrite` 也一样，并且不写入任何内容。位于此类编辑器文件夹内的目标（`<slug>/` 的子文件夹）会被写入，eject 在文本模式下会警告一次，指明默认分叉和编辑器文件夹之外的路径；`--json` 保持静默。它返回 `theme.add` 响应的复制字段作为 `theme.eject` 响应，描述符在其文件列表中，随后是 `missingPackages`，即副本导入但应用未声明的包，以及 `installCommand`，即安装它们的命令，当没有缺失或包管理器未知时为 null。从项目的任何文件夹（具有 package.json 的最近文件夹）出发，默认目标是项目的本地主题根目录，相对 `[path]` 从工作文件夹读取且必须留在项目内，`outputDir` 相对于工作文件夹。`[path]` 中的反斜杠分隔文件夹。Eject 必须拒绝本地主题根目录本身以及其中以项目可使用的另一个主题命名的文件夹，因为 `theme list` 和 `theme add` 从以主题命名的文件夹读取每个本地主题，并指明默认目标。向该处一个具有新名称的文件夹分叉会采用该名称：其 `defineTheme` 名称是文件夹的名称，其入口、描述符和导出采用该名称对应的构建绑定（`acme-ocean` → `acmeOceanTheme.ts`、`acmeOceanTheme.doc.mjs`、`acmeOceanTheme`），因此 `theme build` 和 `theme add` 将其作为该主题读取。`theme template [path]` 从工作文件夹读取 `[path]`，没有 `[path]` 时在项目根目录（具有 package.json 的最近文件夹）写入 `theme.template.ts`；该路径必须留在该文件夹内，其中的反斜杠分隔文件夹。当工作文件夹及其上层都没有 package.json 时，它写入该处并警告，指明如何在项目根目录写入。没有 `--overwrite` 时，它保持现有文件不变。随后其回执会说明 `--overwrite` 是否会替换该文件（`overwritable`），当不会替换时，指明模板的一个可用路径（`alternative`）。
- **FR7 — 包通过导出暴露每个主题以供导入。** 包通过在 `./themes/<slug>` 导出其已构建模块并在 `./themes/<slug>.css` 导出其样式表，使主题可被导入。恰好拥有一个主题的包可以改为导出 `./built` 和 `./theme.css`。当主题需要非系统字体时，包应导出位于 `./themes/<slug>.fonts.css` 的字体样式表，单主题包则为 `./fonts.css`。字体样式表负责加载其字体：它可以用 `@font-face` 规则随附字体文件，或从字体服务导入它们。当主题没有可解析的已构建模块和样式表时，导入必须失败并指明缺少什么；它绝不回退到复制或运行时源码。`integration add theme` 必须写入这些导出，并且当导出的主题模块、样式表或字体样式表无法从打包的 tarball 解析，或当主题同时导出其已构建模块和样式表且其中之一与其源码不匹配时，`integration verify` 必须失败。当导出的模块是 `theme build` 从该源码写入的模块，或它只加载主题自身的样式（DEC-10）时，它与其源码匹配：其每条语句都为副作用导入主题的导出样式表或字体样式表，除了一条语句，它从 `theme build` 写入的模块重新导出全部内容或仅导出其主题，并使用主题的导出名称。只导出该对中一部分或完全不导出的主题，在它导出的每个路径都可解析时仍然可打包，`integration verify` 会对缺少或不匹配的内容发出警告。
- **FR8 — 本地主题像包主题一样被添加。** 项目的本地主题根目录是 `src/themes`：复制版 `theme add` 写入的文件夹，也是 `theme eject` 默认复制到的文件夹，在没有 `src` 文件夹的项目中也是如此。该处的主题目录若与集成主题形状相同（`architecture:cli-surface` INV19），则像包主题一样被列出和导入。其已构建模块和样式表是 `theme build` 在其源码旁写入的文件，其字体样式表（若有）是它们旁边的 `<slug>.fonts.css`。当输入是其自身输出之一时，`theme build` 在加载输入前拒绝它，并指明该输出来自哪个源码；当输入不是主题模块时也是如此。每个输出的头部都从输出的项目根目录指明其源码，因此从任何文件夹构建都会写入相同的输出。在 `--out` 指定的路径，它替换自身早期的输出。当构建的所有输出都可能被写入后，它会替换仍然存在的另一主题源码的输出并发出警告，指明两个源码。`--out` 中的反斜杠分隔文件夹。构建主题编辑器生成的主题（`<slug>.theme.ts` 与 `<slug>.settings.json` 并存）会警告并指明编辑器中根据其设置构建它的命令。向主题编辑器生成的文件夹（文件夹 `<slug>/` 存放 `<slug>.settings.json`）中，针对该文件夹之外源码的 `--out` 会写入该处并警告，指明源码旁的构建和另一个 `--out`。`--check` 在输出过期时以 1 退出，其结果携带 `code: ERR_THEME_STALE`。`--check` 将构建写入的每个输出都列为已检查。仅有缺失的 `.css.d.ts` 样式表类型存根不算过期：检查在文本模式下警告一次，指明缺失的存根，其退出码和结果仍由其他输出决定；`--json` 保持静默。任何其他缺失的输出，包括模块的 `.d.ts` 和 `.variants.d.ts`，都算过期。当 `--out` 指定的路径不以 `.css` 结尾时它会警告，其打印的导入以实际写入的文件命名。`theme build --watch` 在源码或它导入的任何本地文件变化时重新构建。`--check` 和 `integration verify` 将 CRLF 和 LF 行尾视为相同文本。当已构建模块或样式表缺失时，导入必须失败并指明构建命令。当本地主题和包主题共享一个 slug 时，导入会添加本地主题，除非 `--package` 指定包，`theme list` 显示两者及其所有者。复制版 `theme add` 仅按已发布状态解析捆绑主题和包主题。
- **FR9 — 模块只导入已构建主题。** 生成的模块必须导入已构建主题、它们的样式表，以及包导出字体样式表时的字体样式表，绝不为运行时样式注入导入主题源码，因此每个已添加主题在首次绘制时即存在，切换从不等待样式。
- **FR10 — 列表显示应用的主题。** `theme list` 必须将每个主题标记为已添加或未添加、是否为项目的默认主题，并指明它是捆绑主题、来自包还是本地主题。这些字段是附加的，本地主题作为额外条目加入列表。
- **FR11 — Doctor 证明设置正确。** 在有主题模块的项目中，doctor 必须检查，并且只在正面证据上通过每项检查：
  1. 每个已添加主题的所有者都已安装，且其模块和样式表可从项目解析；
  2. 主题模块存在，携带 CLI 的生成标记，并且正是 CLI 根据其携带的记录生成的内容；
  3. 项目源码导入主题模块（无法证明时为警告）；
  4. 没有已构建主题模块在其样式表缺失的情况下被导入；
  5. 每个已添加的本地主题都已构建，且其输出与其源码匹配；本地主题导入而项目缺少的包会使这项检查失败，并指明安装它的命令；
  6. 没有已添加主题直接设置私有 `--_*` 变量（`architecture:theme-compilation` INV6）；
  7. 每个已添加主题的 `@astryxdesign/core` 对等范围接受已安装的 Core；
  8. 默认主题是已添加主题之一；
  9. 已添加主题指明的每个字体族都是系统字体，或由模块导入的字体样式表加载（无法证明时为指明该字体族的警告，例如样式表从字体服务导入其字体时）；
  10. 没有两个已添加主题在其自身主题作用域之外为同一选择器写入不同规则，因为每个已添加样式表都会同时加载。

  每项失败都会指明修复它的确切命令。

- **FR12 — 复制默认值通过其生命周期退出。** 复制版 `theme add`、其选项以及其 `theme.add` 响应是已发布的契约。`theme add` 通过其 `spec:AST-017` 生命周期达到 FR1：
  1. **复制默认值已弃用。** 不使用 `--import` 时，`theme add <slug> [path] [--overwrite] [--package <package>]` 复制主题源码并按已发布状态返回 `theme.add`。它每次调用最多发出一次 stderr 警告，为分叉指明 `theme eject`，为使用主题指明 `theme add --import`，其机器可读结果携带弃用 ID 和替代项（`spec:AST-017/FR28`、`spec:AST-017/FR29`）。其退出状态、规范输出以及机器可读结果的其余部分均为已发布状态。`theme add --list` 在每个阶段都保留其机器可读结果，其文本指明当前阶段的命令。
  2. **清理落在已声明的次版本中。** 当 `main` 声明一个次版本时，描述该变更的 `[breaking]` Changeset（`spec:AST-017/FR31`）允许 `theme add <slug>` 按 FR1 所述执行导入，无论是否带 `--import`，并返回 `theme.app`，且 `theme add` 不再接受目标路径或 `--overwrite`，它们保留在 `theme eject` 上。该次版本不承载本记录的其他差异（`spec:AST-017/FR39`）。

  现有项目按如下方式迁移（`spec:AST-017/FR8`）：

  1. 使用 `theme add` 复制的脚本改用相同参数的 `theme eject`；希望应用使用该主题的脚本改用 `theme add --import`，它在清理后仍保留其含义。没有 codemod 会重写这些调用，因为正确的替代取决于调用者指的是哪一种；弃用警告会同时指明两者。
  2. 由 `theme add` 复制的主题是应用源码。CLI 不得移动、修改或删除它，应用对它的导入继续有效。该副本缺少主题的描述符，因此 `astryx upgrade` 必须提供一个项目 codemod，在本地主题根目录中为每个此类副本旁写入缺失的描述符，并标记为不受维护，从而使该副本成为本地主题（FR8）。该 codemod 不改变其他任何内容，第二次运行也不改变任何内容（`spec:AST-040`）。
  3. 在该 codemod 运行之前，本地主题根目录中存放无描述符主题源码的文件夹不得使主题命令或 doctor 失败。`theme list` 和 doctor 将其命名为未迁移的副本，并给出升级命令，它不会被列为或导入为主题。仅对本地主题根目录，这取代了此类文件夹会使发现失败的规则（`architecture:cli-surface` INV19）。
  4. 没有主题模块的项目保持原样继续工作。Doctor 报告 CLI 不管理其任何主题并指明导入命令；FR11 的检查在主题模块存在后生效。
  5. 设置 `ASTRYX_THEME` 的调用方使用 `theme use` 选择默认主题，或在没有主题模块的项目中使用 `astryx.theme`。

- **FR13 — 每个面向构建者的界面都一致。** 主题指南、集成指南、生成的 agent 文档以及 `init` 的后续步骤必须描述相同的工作流：导入主题、一次性接线模块、通过导出的主题切换、扩展主题以自定义它，以及仅在需要分叉时使用 eject。它们在复制默认值已弃用期间指明 `theme add --import`，在移除后指明 `theme add`。没有界面把复制作为使用主题的方式来教授。
- **FR14 — 搜索找到列表显示的主题。** `astryx search` 必须将 `theme list` 显示的每个主题索引为 `theme` 结果，`--type theme` 可选择它。主题结果必须携带其 slug 作为 `name`、其显示名称、其描述、提供它的包，以及 CLI 当前 FR12 阶段的 `theme add` 命令：在没有 `--import` 的 CLI 中为 `theme add <slug>`，在复制默认值已弃用期间为 `theme add --import <slug>`，在清理后为 `theme add <slug>`（FR13）。主题的 slug 和显示名称是它的名称，其描述是散文（DEC-9）：主题仅通过其描述共享的查询词会将其排为描述提及，绝不会作为名称或关键词匹配，因此该词本身绝不会使主题排在同名、标题或关键词匹配该词的结果之上。搜索主题不得需要 `@astryxdesign/core`，因为列出主题也不需要，所以在应用之外进行的开放搜索也会包含它们（DEC-8）。帮助、清单和 API 参考必须列出 `theme` 域及其结果字段。

### Platform support

- 支持下限：CLI 支持的每个运行时和包管理器，以及每个从 JavaScript 模块导入 CSS 的工具链。
- 不支持的行为：无法从模块导入 CSS 的工具链会自行加载每个已添加主题的样式表；模块仍然导出主题，doctor 检查 4 会指明要加载的样式表。
- 浏览器证据：为生产构建的使用方应用导入一个第一方主题、一个集成主题和一个本地主题，在首次绘制时渲染默认主题，并在三者之间切换。

## Current-state impact

- `theme add` 获得 `--import`；其复制默认值和 `theme.add` 响应已弃用，并在计划中的次版本中离开 `theme add`（FR12）；`theme eject`、`theme remove` 和 `theme use` 加入 `theme` 命令；`theme list` 获得其应用字段并列出本地主题；
- `astryx search` 将 `theme list` 显示的主题作为 `theme` 域找到，并将仅出现在主题描述中的词按散文排序（FR14）；
- `architecture:cli-surface` INV19：集成主题是可导入的包，可编辑源码是显式的 eject；
- `integration add theme` 写入主题导出，`integration verify` 检查它们；
- 在有主题模块的项目中，doctor 的主题检查是 FR11，在无主题模块的项目中是 FR12 报告；
- `astryx upgrade` 携带为副本提供描述符的 codemod（FR12）；
- CLI 停止读取 `ASTRYX_THEME`（DEC-7）；
- 主题指南、集成指南、agent 文档和 `init` 后续步骤描述 FR13 工作流。

## Decision log

### DEC-1 — Consumers import; copying is an author fork

**参考：** `spec:AST-050/DEC-1`

**决定者：** `josephfarina`，`2026-09-30`

应用使用的主题是依赖项，就像组件库：它保留其所有者的更新、其身份，以及其包在它旁边加载的样式表。应用通过扩展主题来自定义它。复制是模板开始一个页面的方式，也是作者分叉主题的方式，而不是应用使用主题的方式。因此使用方的 `theme add` 执行导入，源码复制属于显式的作者分叉 `theme eject`。

已否决：将 `theme add` 保留为复制并为导入添加新动词，这会使最明显的命令对大多数构建者做错误的事。

### DEC-2 — The CLI owns one generated module and never edits app code

**参考：** `spec:AST-050/DEC-2`

**决定者：** `josephfarina`，`2026-09-30`

应用一次性接线一个模块。此后，添加、移除和选择主题只改变 CLI 生成的文件，因此没有命令需要证明它可更改应用源码，而切换器从单一导出读取每个已添加主题。模块有一个永不移动的固定位置，因此应用的导入继续有效，且无需任何设置即可找到它。

已否决：每次导入时编辑应用的根组件，这需要为每个框架做源码转换。

已否决：只打印导入行，这使应用必须手工维护主题列表。

已否决：可配置的模块路径，`spec:AST-017/FR19` 仅在固定位置失败的情况下才允许。

### DEC-3 — The generated module is the record

**参考：** `spec:AST-050/DEC-3`

**决定者：** `josephfarina`，`2026-10-01`

模块已经指明了每个已添加主题、它来自何处以及默认值。别处的第二份记录会重复 CLI 可从其自身输出读取的值，而 `spec:AST-017/FR19` 禁止这样做，并会添加每个应用都必须与模块保持同步的公共字段。

已否决：`package.json` 中的 `astryx.themes` 字段，它会把模块作为永久的公共接口重复一份。

已否决：`astryx.config` 中的键，已发布的 CLI 会将其作为未知键拒绝。

已否决：从应用源码检测主题，它无法区分应用使用的主题和仅被应用提及的主题。

### DEC-4 — Packages expose themes through their exports

**参考：** `spec:AST-050/DEC-4`

**决定者：** `josephfarina`，`2026-09-30`

固定的导出路径让任何应用都能用任何 CLI 版本、或完全不使用 CLI 来导入主题。它不添加描述符字段，因此没有已发布的 CLI 会遇到未知字段。单主题形式保留已构建主题包已使用的 `./built` 和 `./theme.css` 导出名，因此现有包无需新发布即可被导入。

已否决：在主题描述符中声明导入路径，已发布的 CLI 会将其作为未知字段拒绝。

### DEC-5 — New subcommands under `theme`

**参考：** `spec:AST-050/DEC-5`

**决定者：** `josephfarina`，`2026-09-30`

它们每一个都留在 `theme` 命令的职责之内，即管理应用的主题（`spec:AST-042/FR4`）：

- `theme remove` 回答“停止使用此主题”。`add` 上的选项会赋予它第二项职责。
- `theme use` 回答“从该主题开始”。`add` 上的选项无法设置已添加主题的默认值。
- `theme eject` 回答“给我该主题的源码以便分叉”。它是 `theme add` 在复制默认值已弃用期间所做的复制，加上本地主题所需的描述符（`spec:AST-042/FR6`）；一旦复制离开 `theme add`，`add` 上的选项会赋予它两个相反的结果。

它们都不符合批量契约的资格（`spec:AST-042/FR7`、`spec:AST-053/FR11`），因此每个都接受一个选择器：

- `theme remove <slug>` 改变应用的主题：它会使 E1 和 E4 失败。
- `theme use <slug>` 改变应用的主题并选定一个默认值：它会使 E1、E2 和 E4 失败。
- `theme eject <slug> [path]` 写入文件并在 slug 之后接受一个位置参数：它会使 E1、E4 和 E5 失败。
- `theme add <slug>` 在导入时改变应用的主题：它会使 E1 和 E4 失败。

每个都在 `spec:AST-042/FR1` 下有一个 API 函数。

已否决：用一个带各动作标志的 `theme set` 命令，这会让单个命令承担多项职责。

### DEC-6 — The import default arrives in two steps

**参考：** `spec:AST-050/DEC-6`

**决定者：** `josephfarina`，`2026-10-05`

每个替代方案都首先在兼容的补丁中发布：`theme add --import`、`theme eject`、`theme remove`、`theme use`、生成的模块、包导出以及 doctor，同时复制默认值在其警告下继续工作。导入默认值随后在一个由所有者安排的次版本中跟进（`spec:AST-017/FR28`、`spec:AST-017/FR47`），因此每个构建者都能在它成为默认值之前到达导入路径。可选启用是 `theme add` 上的一个选项，因此构建者在弃用期间学到的命令就是之后执行导入的命令。

已否决：在一个版本中切换默认值，`spec:AST-017/FR48` 在 main 面向补丁时拒绝这样做。

已否决：通过主题模块的存在来选择启用，这会在没有可见控件的情况下改变 `theme add` 的行为（`spec:AST-017/FR14`）。

### DEC-7 — The CLI reads no theme environment variable

**参考：** `spec:AST-050/DEC-7`

**决定者：** `josephfarina`，`2026-10-05`

`spec:AST-017/FR14` 禁止 CLI 定义或读取任何 Astryx 拥有的环境变量，因此 `ASTRYX_THEME` 不是选择主题的受支持方式，CLI 在两个阶段都不读取它。应用的默认主题存在于其主题模块的记录中（FR3），或在没有主题模块的项目中存在于 `astryx.theme` 中。

已否决：在次版本之前读取 `ASTRYX_THEME` 并发出警告，这仍然读取了 `spec:AST-017/FR14` 禁止的变量。

已否决：在设置 `ASTRYX_THEME` 时警告，这需要读取该变量才能警告。

### DEC-8 — Searching themes needs no Core

**参考：** `spec:AST-050/DEC-8`

**决定者：** `josephfarina`，`2026-10-06`

`theme list` 无需 `@astryxdesign/core` 即可读取捆绑主题，因此主题搜索也是如此，并且应用之外的开放搜索会包含它们。尚未设置应用的构建者仍可按外观找到主题。

已否决：除文档外每个域都需要 Core，这会使 `theme list` 可用情况下的仅主题搜索失败。

### DEC-9 — A theme's description is prose

**参考：** `spec:AST-050/DEC-9`

**决定者：** `cixzhang`，`2026-10-06`

主题的描述是为选择外观的人写的一句话。它的词描述一种情绪，因此其中的词只是顺带提及，按任何其他描述排序，而不是主题作者为搜索选择的标签。主题的名称是其 slug 和显示名称，并且主题不声明关键词。

已否决：将每个描述词都读作关键词，这会使主题因其描述恰好使用的任何词而排在首位。

### DEC-10 — A theme module may load its own styles

**参考：** `spec:AST-050/DEC-10`

**决定者：** `josephfarina`，`2026-10-20`

包可以使导入主题的模块成为整个集成：模块导入主题的样式表和字体样式表，然后重新导出已构建主题，使用方依赖该导入来加载样式。当这些导入和对已构建主题的一次再导出是其仅有的语句时，`integration verify` 接受该模块。再导出可以给已构建主题赋予主题的导出名称，因为 `theme build` 以主题自身的名称命名已构建模块及其导出，而该名称可能不同于包导出它时使用的 slug。被再导出的模块仍然正是 `theme build` 写入的内容，样式表和字体样式表保持为单独的导出，因此生成的模块像之前一样导入三者，打包器会各加载每个样式表一次。

已否决：要求导出的模块就是已构建模块本身，这会使此类包在通过 verify 与保持其使用方的导入继续工作之间做选择；以及接受任何导出主题的模块，这会让 verify 通过一个不再与其源码匹配的模块。
