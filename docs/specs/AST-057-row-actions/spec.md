## Intent

在手机上，人们把一行侧向轻扫以触达某个动词——归档、删除、标记未读、选择。Astryx 的行不支持轻扫。本记录把该手势加入 `Item` 这一行原语，使 `ListItem` 与产品自身标记中的裸 `Item` 以同样方式滑动。可用范围的规则是行的角色：滑动面板的控件是该行的交互式后代，因此滑动操作存在于角色允许它们的任意行上——`listitem`、完全无角色的行——而不存在于角色禁止它们的行上。这把列表行与独立行归入其中，把 option、menu-item 与 radio 行排除在外，且无需指名任何组件；尚未有人写过的行类型会自行归类。

该手势是面向手指、触控笔与触控板的加速器：它为手指、触控笔或触控板的水平滚动增加一条通往动词的更快捷路径，而对鼠标拖拽、悬停或键盘不改变任何东西。每一侧的动词都作为数据声明——一个命名该动词所到达状态的 label、一个图标、一个处理函数、它的外观，以及行之后是否保持滑出——因此组件在手指移动之前就知道所需的一切：绘制什么、触发什么，以及完成时行停在哪里。行自身的根元素移动，其面板保持不动，因此不向任何行添加元素。

## Ownership boundary

**拥有**

- `Item` 滑动操作的公共形态：`swipe` prop、`createSwipe` 及其选项、`SwipeAction` 及其字段、每侧数组、`swipeBehavior`，以及不透明的 `Swipe` 值。
- 滑动代码所在之处：位于构造函数的模块中，绝不在 `Item` 或 `ListItem` 中，唯有 DEP-0017 在 `Item` 中的已弃用路径例外——已发布的加载器、已发布的行样式、角色门控、`commit` 警告、被加载层填充的桥接、进入该桥接的按键转发器，以及共存诊断——它仅服务已弃用的 props，并随 CLN-0025 在 0.8.0 中离去。
- 滑动操作可用范围的规则：行的角色。
- 两个模型 `reveal` 与 `commit`，在滑动操作可用的任何地方含义相同。
- 手指与触控板行为：静止或触发、加速器、操作后行停在哪里、一次只有一行打开，以及行如何关闭。
- 手势所用的解剖结构：`Item` 既有根元素上的两个脱离流位置、根元素的平移与面板的反向平移，以及组的内联裁剪。
- 手势本身的无障碍契约：面板在静止时与关闭时暴露什么，以及鼠标拖拽与悬停不触碰任何东西。

**为何没有既有记录能承载它**

- [`architecture:interaction-modality`](../../architecture/interaction-modality.md) 是 `current`，拥有该手势必须遵守的规则——INV7“必要操作保持可达”——但不拥有任何公共 API。一条记录只携带一个 `authority` 值，因此把未批准的 API 主张加进去会把它们呈现为已批准（`architecture:knowledge-contracts` INV1、INV14）。
- `Item` 没有组件记录。本记录是关于 `Item` 公共接口的第一个持久决策；`component:Item` 在撰写时继承这些主张，而不是重新决定它们。在 `Item` 的七个核心内渲染器中，有六个给行赋予禁止交互式后代的角色，因而不在范围内；`ListItem` 与调用方标记中的裸 `Item`——系统自身模板在 `BottomSheet` 内和页面上渲染的正是后者——才是本记录服务的行：两个真实使用方、一个归属，prop 仍留在原语上（DEC-3）。
- [`component:List`](../components/List/List.spec.md) 是 `current`，拥有 List 的几何；它获得内联裁剪，并引用本记录。
- [`spec:AST-002`](../AST-002/spec.md) 拥有准入：调用方拥有哪些动词值得一个手势、哪种模型适合它们，而组件两者都无法推导。

## Non-goals

- **行还提供什么。** 行的可见控件——`endContent` 中的菜单或按钮、它自身的主操作（primary）——是 `Item` 既有的组合，不在此处治理、配对或检查。使用方文档陈述该义务；组件不监管它。
- **精细指针上的悬停揭露操作面板**（DEC-4）。
- **为行的退出或进入添加动画。** 此处未定：调用方在操作后移除的行像今天任何行一样卸载。一旦定下，可能的形式是命令式的（`handleRef`，正如 `Selector` 与 `MultiSelector` 暴露 open/close），这样进入也能动画。`hasRemoval` 不是它：它只说明操作后行停在哪里，而保持滑出却从未被移除的行会停在屏幕外——那是调用方的缺陷，而那个最终 API 正是让这种情形变得体面的手段。
- **自定义面板的 render prop。** 推迟，但未排除：当调用方需要词汇表无法表达的东西时，可以加入一个 `render*` 形状的扩展（DEC-1）。
- **手势调参。** 轴锁定距离、提交比例、甩动速度、越过面板后的阻力，以及滑动驱动的位移与弹簧：这些都是源码中的行为常量，不是公共 API，也不是设计 token（与触摸按压模型为其时钟参数所得到的裁决相同）。由轻点或 Escape 启动的关闭从静止开始播放行的弹簧（FR7，`spec:AST-094` FR45）。
- **垂直滑动**，以及唯一含义为关闭的滑动（Toast 已在 `useToastGesture` 中有此能力）。
- **`Item` 上的公共脱离流插槽。** 刻意不予准入：面板位置是内部的，由 `swipe` 渲染。第二个使用方——强调条、滑入式复选框、拖拽把手——需要一条 `component:Item` 解剖记录及其自身的准入论证。
- **非 `Item` 元素上的滑动操作。** `createSwipe` 配置的是 `Item`；把其结果附加到任何其他元素上不予准入。
- **程序化的打开或关闭。** 不予准入：滑动面板的打开状态属于手势，而实践中遇到的唯一协调情形——静止的行在相邻行开始拖拽时关闭——已经是行外指针（FR7）。没有产品提出过请求，而该手势所模仿的行也不暴露此类句柄。若真有需要，`handleRef` 是既定的添加模式，正如 `Selector` 与 `MultiSelector` 暴露 open/close/toggle。
- **角色禁止交互式后代的那些行。** 滑动操作在角色允许交互式后代的行上可用，因为滑动面板的控件是该行的交互式后代；`listitem` 与无角色的 `Item` 符合条件，在那里“它自然就能工作”。角色禁止它们的行则因故不在范围内：`option`（位于 `listbox` 内）、`menuitem`、`menuitemcheckbox`、`menuitemradio`，以及作为原生单选钮放大目标的那些行。这是范围边界，而非每次调用或每种模型的限制，因此 `swipeBehavior` 在滑动操作存在的任何地方含义相同。在今天的 core 中，这排除了 `SelectorOption`、四个 `DropdownMenu` 行和 `RadioListItem`，而包含 `ListItem` 与每个裸 `Item`。
- 当满足本契约时，等效的内部实现仍然有效。内部模块、文件、函数名、算法、数据结构、存储布局、清单、日志、锁、事务协议，以及 CI 作业/工作流拓扑，属于架构或实现，除非调用方或互操作系统有意依赖该确切机制作为公共协议。

## Cases the contract serves

| 情形                                                            | 是否支持 | 如何                                                                                                                                                                             |

### Accessibility contract

- **AR1 — 面板在静止时是真实的，在关闭时是不存在的。** 在 `reveal` 下，当行静止打开时，每个条目必须是由 `label` 命名的、真实可聚焦的 `<button>`，这样落在其上的触摸屏阅读器就能激活它；关闭时，面板必须不在无障碍树和 Tab 顺序中。在 `commit` 下，面板必须在任何时候都是呈现性的（`aria-hidden`），因为其中的任何东西都永远不可点击。
- **AR2 — 鼠标拖拽永远不会滑动行。** 鼠标拖拽与悬停不得露出面板，并且在可悬停的指针上，关闭行的 `swipe` 不得对 Tab 顺序、无障碍树或行的绘制产生任何影响。触控笔的拖拽（`spec:AST-094` FR43）或触控板的横向滚动可以露出面板（DEC-7），而它留在静止打开状态的行遵循 AR1；鼠标滚轮的刻度则不得。
- **AR3 — 行的主要元素始终是一个 Tab 停靠点。** `swipe` 不得改变主要元素的角色或名称，不得在行关闭时改变其激活方式，并且在关闭时不得增加停靠点。当行打开时，在其内容上的触摸轻点会关闭它（FR7）；键盘激活保持不变。
- **文档中声明，而非强制执行：** 滑动是一种触摸加速器，因此只能通过滑动到达的动作，用键盘和鼠标拖拽都无法到达。`swipe` 的使用方文档必须说明这一点，并且必须展示该动作也可以通过行自身的内容到达。组件不检查行还提供了什么。

### Platform support

- 受支持的功能/引擎下限：每个受支持的渲染器与浏览器。手指或触控笔的滑动从其指针事件读取；触控板的从横向 `wheel` 手势读取，后者没有指针类型。鼠标滚轮的刻度永不滑动（`spec:AST-094` FR43），鼠标拖拽也永不滑动。
- 不支持的行为：没有触摸屏、没有触控笔、也没有触控板的设备不会获得滑动，鼠标拖拽也永不滑动；其他一切不变。
- 浏览器证据：FR2 和 FR4–FR9 是绘制与手势主张。jsdom 两者都没有；需要带派发触摸事件的真 Chromium 证据，并且 FR5/FR6 还需要物理触摸设备，因为该手势的 Chromium 证据尚未能预测设备行为。

### DEC-1 — Swipe actions are declared as data

**Reference:** `spec:AST-057/DEC-1`

**决策者：** `cixzhang`, `2026-10-02`

`createSwipe` 的 `leading` 与 `trailing` 是 `SwipeAction[]`：`{id?, label, icon?, onActivate, isDisabled?, variant?, hasRemoval?}`。`Item` 渲染每一个条目——在 `reveal` 下作为真正的按钮，在 `commit` 下作为展示性块——并在拖拽期间依据数据绘制该面板。

当组件渲染该事物时就需要对象；当组件只放置它时节点即可（`spec:AST-058` DEC-1 从另一侧划出同一条界限，其 picker 行动作是节点，因为 picker 只把它们放进一个单元格）。`Item` 绘制并动画化面板，因此每个字段在手势开始之前就已知；调用方自己的节点若不通过上下文注册，两件事都做不到，而这会把 API 分裂为获得行为的节点与静默不获得行为的节点。Core 已经通过 `DropdownMenu.items` 与 `MoreMenu.items` 把动词声明为数据，并且两个独立的 vibe-test 回忆探针——一个针对本记录，一个针对 `spec:AST-058`——发现每个构建者都恰好伸手去拿这个数组，且未给出任何 prop 名称，没有人伸手去拿子组件或渲染 prop。

这套词汇：`onActivate` 是 core 用来表示一行的动词经由非点击路径触发的词（`useMenuPress`、`useTreeFocus`、`Selector`、`TreeList`），而 commit 在释放时触发，完全没有点击。`variant` 是 `'neutral' | 'accent' | 'destructive'`，默认 `accent`（DEC-6）。`label` 命名该动词所抵达的状态（"Unread"），因为面板与它所揭开的标题共享同一行宽度，而手势已经提供了动词。`hasRemoval` 是组件无法推断的一个位：动作触发之后，行是弹回还是撑住？它独立于 `swipeBehavior`——commit 不是移除，而在停驻的 "Archive" 上轻点则是——也独立于 `variant`，因为 Archive 离开时并非破坏性，而带 Undo 的柔和 Delete 是破坏性的而该行却留下。它取名 `has*`，因为它声明的是动作的一个属性，而不是行所处的状态。它不过是停驻位置：不是调用方会移除该行的承诺，因此没有义务也没有警告；不是动画，因此不会有任何东西塌缩或淡出；不是时序规则，因此 `onActivate` 仍在激活时触发。

组合被推迟，而非丢失：为词汇无法绘制的面板增加 `render*` 形状的扩展，可以在调用方需要时落地。被撑住的行如何离开，以及被保留的行如何返回，不属于本记录（非目标）。

已否决：每侧放置节点并附带一个已发布的 `SwipeAction` 组件——它需要为 `commit` 做上下文注册，并让任何调用方提供的节点静默地没有它。已否决：每侧一个动作，配 `onAction` 与四声调的 `tone`——那是第二套动词词汇。已否决：更宽的 `hasRemoval`，它承诺调用方会移除该行、拥有退出动画，并在其后触发 `onActivate`——那会把确认优先的删除变成例外，并把停驻位与未落定的退出动画绑在一起。已否决：`isCommitExit`——该位在 `reveal` 下也适用，因此以 commit 命名它是错的。

### DEC-2 — Rest is the default; commit is a caller choice for one verb

**Reference:** `spec:AST-057/DEC-2`

**决策者：** `cixzhang`, `2026-10-02`

`swipeBehavior: 'reveal' | 'commit'`，默认 `reveal`。在 `reveal` 下，行停驻为开启，长拖拽会触发最外层条目；在 `commit` 下，行滑出，最外层条目触发。滑出就是手势自身的确认；此后行停在哪里由条目的 `hasRemoval` 决定，而不是该模型——commit 不是移除——并且组件在触发之后不等待任何东西。`commit` 在每个拥有 swipe 动作的行上含义相同；没有宿主会收窄它。

在平台两者都提供的地方，完整滑动是依据停驻列表定义的——UIKit 的标志是 [`performsFirstActionWithFullSwipe`](https://developer.apple.com/documentation/uikit/uiswipeactionsconfiguration)，它对停驻的动作做索引——因此停驻是承载多个动词的模型，而 commit 是恰好承载一个动词的模型；数量与停驻状态是同一个问题，这就是一侧有多个条目的 `commit` 会警告的原因。停驻的面板还让触摸用户在破坏性动词触发之前有东西可看，这就是它是默认值的原因。保留 commit 是因为两种模型都被需要，而且它也是这个手势所参照建模的那一行在其单动词行上所用的东西。

已否决：把 commit-only 作为唯一模型——它无法在不改变默认值的情况下成长为停驻。已否决：布尔 `hasFullSwipe`——在 `reveal` 下完整滑动已经开启，而在 `commit` 下它就是全部行为，因此布尔把控的是错误的轴。已否决：`hasCommitAnimation` 标志——滑出就是 commit 确认的方式，而 `commit` 已经决定了它；为同一件事再加一个开关，就是 `hasCreate` 上被否决的布尔加处理器式重复。已否决：要求行在每次 commit 之后都留在外面（#6821）——一行已提交的 "Mark read" 仍然在那里。

### DEC-3 — The capability is `Item`'s; where it is available follows the row's role

**Reference:** `spec:AST-057/DEC-3`

**决策者：** `cixzhang`, `2026-10-03`

`Item` 拥有 `swipe`。`ListItem` 通过其既有透传继承它，自身不声明任何东西；产品自有标记中的裸 `Item` 以同样方式获得它们。swipe 动作在何处可用遵循一条规则：行的角色必须允许交互式后代，因为 swipe 面板的控件是该行的交互式后代。`listitem` 与无角色的 `Item` 合格；`option`、`menuitem*` 角色，以及作为原生 radio 放大目标的那些行不合格，且在范围之外——不收窄到某一个模型，不按调用逐个警告，只是不提供服务。用关于角色的规则而不是组件列表，意味着没人写过的行类型会自我归类，而范围边界让 `swipeBehavior` 在它存在的每个地方都只意味着一件事。打开状态是行自己的：指针落在停驻行之外的任何地方都会关闭它，而在相邻行上的拖拽就是这样一个指针，因此一次只有一行停驻为开启，没有组状态，也没有协调 hook。

只有拥有根的组件才能平移它，而行外的包装器被 HTML 列表内容模型排除——它会坐在 `<ul>` 与 `<li>` 之间——因此手势必须住在根所在之处。在 `Item` 的七个核内渲染器中有六个给该行一个禁止交互式后代的角色；第七个是 `ListItem`，而系统自身的模板在任何列表之外渲染裸 `Item`，因此该能力有两个使用方而非一个，这就是它留在原语上的原因：列表行与独立行共享同一个家，而被排除的行是因角色被排除，不是因为 prop 住在哪里。

已否决：既然 `Item` 的七个核内渲染器中有六个在范围之外，就把该 prop 移到 `ListItem`——那会把它只放在最常被使用之处，并把它从独立行拿走，而独立行是系统自身模板所渲染的真实使用方。已否决：按模型分别决定范围——在禁止 `reveal` 之处允许 `commit`——因为那会把一个设计选择（行被滑动时做什么）耦合到一个结构约束（宿主可以包含什么），于是同一个 prop 值会因宿主而行为不同。已否决：由宿主组合的行为 hook——一次只开一个是它作为组状态存在的理由，而外部关闭以不共享任何东西的方式给出同样的结果。已否决：命令式或受控的打开——没有人要求过，而且手势已经拥有那唯一的协调场景。

### DEC-4 — No hover reveal

**Reference:** `spec:AST-057/DEC-4`

**决策者：** `cixzhang`, `2026-10-02`

鼠标拖拽与悬停在 `swipe` 上什么都不做；水平滚轮输入、触控板的滚动或鼠标的水平滚轮，以及笔，是会滑动一行的非手指输入（DEC-7）；一行提供给鼠标或键盘的是该行自身的内容，本记录不治理它。

已否决：在精细指针上把同样的动作渲染为悬停揭开的按钮的揭示轴——那是行内容已经可以承载的动词的第二个表面。[React Aria 的 iOS 列表示例](https://react-aria.adobe.com/examples/ios-list) 走的就是那条路线（树中的一个面板按钮，在焦点时揭示），也是本决策搁置的替代方案。

### DEC-5 — The root translates and the panels counter-translate; no element is added

**Reference:** `spec:AST-057/DEC-5`

**决策者：** `cixzhang`, `2026-10-02`

`Item` 把每一侧的面板渲染为其既有根的一个绝对定位子级，位于内联起始或结束处，在根背景之上、内容之下。拖拽把它的位移写成根上的一个自定义属性——就像 `useToastGesture` 写 `--_toast-swipe-y` 那样——根的 transform 读取它，每个面板的 transform 读取它的相反数，于是行移动，而面板出现在行腾出的空间里并保持固定。两者都是合成器 transform，抵消是精确的。任何行都不新增元素。组用 `overflow-inline: clip` 裁剪。这些位置是内部的：不为它们接纳任何公开 slot。

分层与平移是不同的问题，两者都不需要新元素。分层是根已提供的包含块内的绝对定位，并在根上设置 `isolation: isolate`，使面板上的负 `z-index` 保持在局部（2026-09-04 的 isolation 裁定）。平移是根自身的 transform：内容在每种渲染模式下都是四个兄弟，而根已经是它们的共同父级。根自身的样式在 transform 之后仍然有效——它上面没有 `overflow` 或 `contain`，focus-within 轮廓与主题 target 随它一起移动。裁剪不能是行的，因为行正是移动的东西，所以它是组的；`hidden` 会创建滚动容器并与列表的纵向滚动器对抗。

已否决：在 `Item` 内部放一个包装元素，无论是否条件渲染——那是 CSS 与测试要跨骑的第二种行形状，为一个根的 transform 已经解决的问题。已否决：围绕新的内层行放一个裁剪容器——那会在每个滑动行上增加一个元素。已否决：把面板作为列表层的兄弟，按每行的偏移定位——那是一个针对 resize、重排与虚拟化挂载的位置同步循环。已否决：在根上动画化 `padding-inline-start`——在手指下每帧都做布局，而不是合成器 transform。已否决：公开 `beforeContent` / `afterContent` slot——本记录中没有任何东西需要它们，而通用解剖结构有其自己的接纳程序。

### DEC-6 — The verb variant set is `neutral | accent | destructive`, minted knowingly

**Reference:** `spec:AST-057/DEC-6`

**决策者：** `cixzhang`, `2026-10-02`

`ItemSwipeActionVariant` 是 `'neutral' | 'accent' | 'destructive'`：三种动词风味——普通的、你真正指的那个、危险的那个——而 `accent` 在 swipe 面板上是默认值，因为面板是一个必须具有某种颜色的填充表面，而 `ProgressBar` 已经把填充表面默认为 `accent`。

这是新造的词汇，而非复用，并且是在知情的情况下采取的：在 core 中，除 `ProgressBar` 的默认值之外，`accent` 不出现在任何其他 variant 枚举上，而 `Step.status` 把它作为状态携带。共享的状态集——横跨七个组件的 `success | warning | error`——命名的是状态，而动词不是状态："Archive" 不是 success，"Delete" 也不是 error。`spec:AST-058` 为 picker 行动作采用同一集合并以 `neutral` 为默认值，因此在动词获得颜色的两个表面上，词汇是同一套。

已否决：状态集——它会让动词声称一个状态。已否决：`tone: 'accent' | 'success' | 'warning' | 'error'`——一个带有一个装饰性成员的状态集。已否决：`Badge` 的 variant 映射——它携带装饰性颜色（`blue`、`cyan`、……），而动词槽位绝不能接纳这些。已否决：菜单行的双值 `'default' | 'destructive'`——它对面板存在所要提供的那个动作没有词。

### DEC-7 — A trackpad swipes a row; a mouse drag does not

**Reference:** `spec:AST-057/DEC-7`

**决策者：** `cixzhang`, `2026-10-26`

触控板的两指水平滚动与手指的滑动是同一个动作，并且不从页面取走其他任何东西，因此它像手指一样揭示并触发行动作（`spec:AST-094` FR43）。鼠标拖拽会取走浏览器的文本选择与原生拖拽，所以鼠标拖拽从不滑动一行。鼠标的水平滚轮发出与触控板相同的事件，并以相同方式滑动。

已否决：让 swipe 动作保持仅触摸。

修正（与 `spec:AST-094` FR43 保持一致）：触控板的水平滚动 MAY 揭开面板；鼠标滚轮的格数不行。

### DEC-8 — Swipe actions are configured through a constructor

**Reference:** `spec:AST-057/DEC-8`

**决策者：** `cixzhang`, `2026-11-01`

`Item` 接受一个 prop，`swipe`，其值来自 `createSwipe(options)`。选项保留 DEC-1 的条目与 DEC-2 的两种模型；一个 `swipeBehavior` 治理两侧。swipe 的所有代码——共享手势核心、动画器、面板的渲染，以及该行的手势代码——都住在构造器的模块里，该模块静态导入它。`Item` 不携带其中任何东西，因此应用只在导入 `createSwipe` 时才为 swipe 付费，打包器在其他所有地方把它丢掉，运行时不加载任何东西。这是 `architecture:public-component-api` INV19 为资源开销很大的功能给出的插件路径，也是 CodeBlock 已经用 `language={createCodeLanguage(…)}` 采取的形状。

已否决：在行首次拥有 swipe 动作时用 `import()` 加载 swipe 代码——那会让手势只在行绘制之后才存活，并需要对 `architecture:react-component-runtime` INV13 静态导入的例外。已否决：把数据留在 `Item` 的 props 上并静态导入——那会把手势核心放进每一个渲染行的导入里。

### DEC-9 — A flick reveals; only a deliberate drag fires

**Reference:** `spec:AST-057/DEC-9`

**Decider:** `cixzhang`, `2026-11-10`

轻扫绝不触发条目。一次短促快速的滑动会让行停在展开状态，露出这些操作，正如 FR5 的速度规则所述；要到达确认点需要一次刻意的拖动，因此若释放时的位移来自轻扫的速度而非手指自身的距离，就不会确认。在有两个或更多条目的一侧，整滑只有在从最外侧条目已展开的面板开始的拖动下、或从静止的展开行到达确认点时才确认；从行内容开始并越过确认点的滑动则改为停在展开状态。当行处于展开状态或整滑已确认时，每个未被覆盖的像素都显示拥有它的条目，因此条目的背后或之间都不会露出其他条目的颜色。触发某个条目不会绘制任何中间帧：面板与行在滑动与条目结果之间绝不闪烁。

所有者：“一次小幅轻扫至少应停在大约只显示选项的位置，然后用更长、更刻意的动作来执行默认操作……如果有两个选项，我们就要避免用轻扫来激活，只有当你刻意从 delete 上开始滑动或轻扫时才激活该滑动操作”。关于 Delete 操作：“delete 操作的闪烁绝对不可接受”。

已否决：用速度阈值触发最外侧条目的方案（快速轻扫会误删）。

### DEC-10 — Each action has an id, and its handler receives the id and the row's key

**Reference:** `spec:AST-057/DEC-10`

**Decider:** `cixzhang`, `2026-11-10`

每个 `SwipeAction` 都有一个必填的 `id`。`createSwipe` 以字面量推断这些 id，它返回的 `Swipe` 在其类型中携带它们。`onActivate` 接收该操作的 `id` 与行的 `itemKey`：即在触发它的 `ListItem` 上的 `itemKey`，在普通 `Item` 上则为 `undefined`。因此一份定义可服务每一行。调用方在模块作用域定义一次，或在处理函数需要组件状态时于 `useMemo` 中定义。行以这些 id 作为其滑动的键。id 相同的新值会让行保持原样；id 不同的新值会关闭已展开的行。变体与行为类型保留其已发布的名称：`ItemSwipeActionVariant` 与 `ItemSwipeBehavior`。

所有者：“好的，按操作来，并设法让它可被记忆化，这样我们就不需要重新创建 createSwipe”，以及“rowSwipe 类型应携带滑动操作的 id，用于 onSwipeAction”。

已否决：行级的 `onSwipeAction` 属性，即在每个操作自身的处理函数旁边再加一条处理路径。已否决：以 id 为键的处理函数映射，即与操作保持同步的第二个地方。已否决：行上的 `value` 属性；滑动不持有值。
